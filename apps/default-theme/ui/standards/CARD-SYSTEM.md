# LoveCards Feed Card System

> 状态：v1.1 设计规范。本文定义信息流卡片的家族、密度、媒体与交互状态；模式注册和规则能力见 [`../docs/registries/CARD-PATTERNS.md`](../docs/registries/CARD-PATTERNS.md)，交互表面见 [`../docs/specifications/INTERACTIONS.md`](../docs/specifications/INTERACTIONS.md)。

## 1. 设计命题

LoveCards 的卡片不是重复出现的白色容器，而是一组共享系统语法的内容材料。它们需要同时做到：像小红书一样快速判断媒体与兴趣价值，像 Twitter/X 一样保持作者、时间、来源、引用和讨论上下文，并以接近 iOS 系统组件的精度完成反馈与展开。

卡片的创新集中在三个位置：

1. **轮廓由内容决定。** 文本、图像、图集、视频、GIF、引用、讨论和社区邀请的视觉重心不同。
2. **材质由层级决定。** 常驻内容不透明；玻璃只用于媒体上的临时操作；深度以色调、裁切和状态连续性表达。
3. **身份在状态间连续。** 悬停、喜欢、播放和展开改变状态，不替换组件；进入详情时保留媒体、作者和操作的位置关系。

## 2. 共享骨架

所有卡片使用同一语义顺序，便于阅读器、键盘、响应式布局和未来组件框架复用：

1. **Context / 作者与来源：**头像、作者名、身份标记、时间、地点或推荐原因、更多操作。
2. **Content / 内容：**标题、正文、话题、引用说明或讨论问题。
3. **Media / 媒体：**单图、图集、视频、GIF、链接预览；没有媒体时该层不存在。
4. **Actions / 操作：**Compact 信息流只显示被动互动数据与更多菜单；喜欢作为详情页明确动作，收藏、复制链接和举报收进更多菜单。其他密度只显示当前任务真正需要的动作。

紧凑发现卡允许把 Context 折叠到媒体下方的元数据栏，但作者与来源不能消失；DOM 与无障碍阅读顺序仍保持 Context 在 Content 之前。点击头像只进入身份页，点击内容主体进入详情，点击话题进入对应话题，三个热区不得互相覆盖。

### 基础尺寸

| 项目 | Compact / 发现卡 | Standard / 关系卡 | Detail / 展开 |
|---|---:|---:|---:|
| 理想宽度 | 180–280px | 520–680px | 680–760px |
| 外圆角 | 12px | 12px | 桌面 12–16px；移动端贴边可为 0 |
| 文字内边距 | 10–12px | 14–16px | 20–24px |
| Context 高度 | 32–40px | 44–48px | 48–52px |
| Action 高度 | 36–40px | 44–48px | 48–52px |
| 卡片间距 | 10–16px | 12–16px | 20–24px |
| 正文 | 13px / 1.6 | 15px / 1.65 | 15–16px / 1.75 |

圆角遵守同心几何：当媒体内嵌时，内圆角等于外圆角减去可见内边距；当媒体贴边时，它直接继承对应外角。禁止外层 12px、内层 16px 造成反向圆角。

### 卡片密度

- **发现流：**媒体与主题判断优先。宽屏为 3–4 列，平板为 3 列，360–760px 手机为 2 列；小于 360px 允许单列。元数据栏保留作者、被动喜欢数、评论数和一个三点菜单；卡片不直接点赞或收藏。收藏、复制链接和举报进入更多菜单，喜欢进入详情，不复制完整操作栏。
- **关注流：**人物与时间上下文优先。所有设备均使用单列 Standard 卡；宽屏只扩大两侧留白，不无限拉宽正文。
- **详情与讨论：**沉浸阅读优先。主阅读轴不超过 760px，完整显示操作与讨论关系；相关内容位于主轴外，不能挤压正文。

## 3. 材质与几何

### Content material

- 默认使用不透明 `#ffffff`；画布为 `#f7f8fa`，次级表面为 `#f2f4f7`。
- 引用、选中讨论或社区邀请可使用 `#fff0f3`，但同一屏不连续堆叠多张玫瑰底卡。
- 静止卡片使用 1px `#e5e7eb` 分隔或极轻 `0 1px 3px rgba(20,25,35,.05)`，二者按背景选择其一。
- 暗色模式一一映射为 `#101216`、`#171a20`、`#20242c`、`#2c313a`，不增加霓虹和发光。

### Transient liquid material

只有播放、音量、页码、媒体更多操作和临时提示可以覆盖媒体并使用半透明深色材质。控件底必须随媒体明暗自适应，最小保证图标 3:1、文字 4.5:1；背景模糊是可选增强，不是可读性的唯一来源。

### Icon and hit area

- 图标使用 18–20px、约 1.75px 圆端线条；激活态优先使用系统填充形变，而不是换一套图标。
- 移动端触控热区至少 44×44px；Compact 卡可视觉上只显示 18px 图标，但命中区不能缩小。
- 喜欢用玫瑰色；收藏使用近黑/反白填充，以免两个动作语义混淆；回复和分享默认使用次文本色。

## 4. 卡片家族

### 4.0 模式注册优先

每个 `data.kind` 必须先在卡片模式注册表登记，再映射到本节的轮廓。Feed、Detail、Search 共享同一个模式定义；页面不得自行发明同名模式或用 `data` 越权打开后端未提供的操作。未知模式安全降级为文字模式并报告开发告警。

### 4.1 Text / 文字想法

**角色：**承载短想法、生活记录、观点和纯文字动态。视觉重心是阅读节奏，不用假图片填空。

- **轮廓：**正文直接成为主表面；顶部 Context 与底部 Actions 对齐同一内容轴。允许比媒体卡更大的上下留白，不额外嵌套白色正文框。
- **Compact：**正文显示 4–6 行；超出后以真实文本截断并提供“展开”，不得渐变遮字。标签最多 1 个。
- **Standard：**正文显示 8–12 行后折叠；提及、话题和链接保持可辨识但不高饱和。
- **长文：**在详情中完整显示，行宽 65–75ch；信息流只提供摘要和明确的继续阅读入口。
- **禁止：**为纯文字内容生成无意义封面；使用巨大引号把普通动态伪装成名言。

### 4.2 Single Image / 单图故事

**角色：**让一张图片承担主要发现价值，同时保留作者和内容语境。

- **比例：**优先支持 4:5、1:1、3:2 与 16:9；极端长图在信息流中预览并显示“长图”提示，详情再完整展开。
- **裁切：**尊重服务端焦点或主体检测；不得为了卡片等高切掉人脸、文字主体或商品关键信息。加载前用 `aspect-ratio` 预留空间，避免布局跳动。
- **Compact：**媒体可贴边成为主表面，标题 1–2 行，作者、喜欢数和评论数进入下方同一元数据栏；不在媒体上方重复作者头，不绘制常驻操作栏。
- **Standard：**Context 在上、文字在媒体前或后按叙事顺序出现，完整 Actions 在下；图片最多占首屏约 70%，避免强占屏。
- **角标：**“长图”“敏感内容”“AI/编辑说明”等是语义角标；页数不用于单图。

### 4.3 Gallery / 图集

**角色：**快速表达多张图片的关系，而不是把第一张图伪装成单图。

- **2 张：**等宽双格；根据素材方向选择横向或纵向分割。
- **3 张：**一张主图占约 2/3，另外两张等分剩余区域。
- **4 张：**2×2 同心网格；超过 4 张在最后一格显示 `+N`，详情再展开完整画廊。
- **间隙：**Compact 为 3–4px，Standard 为 4–8px；所有格子的交界圆角由外轮廓统一计算，禁止每张图各自成为小卡片。
- **页码：**如使用轮播，页码放在媒体右上角的临时深色材质中；键盘和触控均可切换，并播报“第 n 张，共 m 张”。
- **详情：**保持首图或当前图的匹配位置，展开后允许缩略导航；返回时恢复原卡片与滚动位置。

### 4.4 Video / 视频

**角色：**在信息流中提供明确、可控的动态内容，不把产品变成连续自动播放平台。

- **海报：**与图片使用相同比例规则；中央播放键为 44–56px 深色自适应控件，时长位于左下或右下。
- **播放：**默认静音且不抢焦点；是否自动预览由产品策略决定，但不得自动出声。离开可视区后暂停或进入明确的小窗状态。
- **控制：**播放后以 150–300ms 淡入自适应控制背景；播放/暂停、进度、静音、全屏必须可键盘操作。
- **字幕：**有声音或对白的视频必须提供字幕入口；重要视频提供文字摘要或转写。
- **Compact：**最多保留播放、时长和静音状态；完整进度与全屏进入 Standard 或详情。
- **禁止：**常驻大面积玻璃控制层、无提示循环、用播放动画阻塞正文。

### 4.5 GIF / 动图

**角色：**表达反应、表情或短循环，与普通图片明确区分。

- 媒体左上或右上显示简洁 `GIF` 标记，使用深色自适应材质。
- 初次进入视口可播放；失焦、离开视口或用户开启减少动态效果时显示静态首帧，并提供“播放动图”操作。
- 悬停、聚焦或触控后出现暂停控制；用户暂停状态在当前会话保持。
- 低数据模式优先加载静态预览，不能用空白或无限 Spinner 替代。

### 4.6 Quote / 引用

**角色：**突出被引用内容与引用者观点的关系。

- **轮廓：**卡片主表面可使用 Rose Mist 或中性浅色材质；引用正文拥有更大上下留白与 15–17px 字号。
- **层级：**引用者观点在前，被引用内容在后；原作者和来源清晰可点击。引用关系通过语义标签、间距和 1px 中性分隔表达。
- **署名：**置于引用正文下方，不能只写一个无上下文名字。
- **禁止：**彩色粗侧条、嵌套第二张卡、装饰性巨大引号压过正文。

### 4.7 Discussion / 讨论与线程

**角色：**让用户在信息流中看见“正在讨论什么、谁在参与、是否值得加入”。

- 顶部显示发起者与问题；正文可包含观点或事件上下文。
- Compact 只显示参与人数、回复数和一个最高上下文价值的回复摘要；Standard 可显示 1–2 条回复，使用分隔与缩进，禁止回复内再套卡片。
- 线程连接线最多 1px、使用中性色；层级主要由缩进、头像和作者重复关系表达。
- “加入讨论”是明确动作；回复、转发、引用和分享必须使用不同标签或可理解图标。

### 4.8 Creator / Community / 创作者与社区

**角色：**承载创作者身份、官方主题、社区邀请和未来生态入口，不伪装成普通用户动态。

- **Creator：**头像、名称、身份说明和关注动作优先；最多展示 2–3 个代表内容缩略图，不做数据仪表盘。
- **Community：**明确标注官方/社区来源、主题说明、参与人数与单一主动作。允许使用 Rose Mist 或主题图片形成更强轮廓，但主动作使用 Accessible Deep Rose。
- **Sponsored / 商业扩展：**未来商品或赞助必须有明确标签；商品信息作为内容的附加语义，不把所有普通卡片替换成商城卡。
- **禁止：**用等级、炫光、金币、连续签到或夸张数值制造手游化身份。

## 5. 交互状态矩阵

所有类型至少实现下列状态。状态变化发生在卡片自身或对应动作附近，禁止用打断式成功弹窗。

| 状态 | 视觉变化 | 时间与曲线 | 约束 |
|---|---|---|---|
| Default | 不透明表面，色调或 1px 分隔定义边界 | 无 | 静止时不漂浮 |
| Hover | 上移 1px或表面明度 +2%；可轻微改变分隔色 | 150–180ms，ease-out | 只在支持 hover 的设备启用；不加宽阴影 |
| Focus | 2px Deep Rose 轮廓 + 3px 低透明外圈 | 即时进入，120ms 淡化 | `:focus-visible`；不能被 `overflow:hidden` 裁掉 |
| Press | `scale(.97)` 后回到 1；媒体与文字一起响应 | 100–140ms | 可中断；不移动布局，不弹跳 |
| Liked | 心形从轮廓变 Signal Rose 填充，计数同步更新 | 160–220ms | 可使用一次轻微符号形变；减少动态下即时切换 |
| Saved | 书签由轮廓变近黑/反白填充 | 150–200ms | 不与喜欢共用玫瑰色；保存失败就地回滚并说明 |
| Playing | 海报转为视频，控制背景短暂淡入；保留喜欢等状态 | 150–300ms | 默认不出声；焦点留在触发控件或播放器 |
| Loading | 与最终结构匹配的 Skeleton；媒体保留比例 | 800–1200ms 周期 | 减少动态下静态占位；卡片高度不能跳变 |
| Error | 失败区域显示原因、替代内容和重试 | 即时 | 局部错误不让整张卡消失；操作失败可恢复 |
| Expanded | 卡片匹配位置进入详情，媒体、作者、圆角和操作连续 | 220–320ms | 返回恢复原滚动位置；减少动态下交叉淡化或即时切换 |

### 状态细则

#### Hover

鼠标悬停只表明“可进入”，不把每个操作都提前高亮。动作图标可从 `#667280` 向 `#1a1a1a` 过渡；卡片主体和按钮不得同时上浮，避免双重运动。

#### Focus

整卡可进入详情时，整卡获得焦点；内部头像、链接和动作仍保留独立 Tab 顺序。整卡不应包裹所有内部按钮成为嵌套交互元素。Focus Ring 必须在浅色、暗色和媒体背景上都可见。

#### Press

按下缩放从指针或触点附近产生视觉接触感，松开立即返回。若卡片包含视频或轮播，按下媒体控制不能同时触发整卡缩放和详情跳转。

#### Liked and saved

喜欢只在详情等明确互动表面提供直接控制，可以使用一次系统符号式填充与最多 8% 的瞬时放大，不使用持续粒子、爆炸或弹簧。收藏在信息流更多菜单或详情操作区使用中性填充；二者先做乐观反馈，失败时在原位置回滚并显示简短原因。

#### Loading and error

Skeleton 必须复制 Context、正文行数、媒体比例和 Actions 的大体结构；禁止一套万能灰条。图片失败保留原比例并显示替代文本与“重试”，视频失败保留海报，回复失败保留用户已输入内容。

#### Expanded

优先使用 View Transitions 或组件库的布局动画能力完成匹配转换，但规范不依赖具体框架。展开时：

1. 媒体保持当前帧、当前图和播放状态；
2. 作者信息扩展为完整身份栏；
3. Compact Actions 过渡为完整 Actions，而不是瞬间换位置；
4. 桌面详情保持 680–760px 阅读轴，移动端允许表面贴边；
5. 返回信息流后恢复原卡片位置、焦点和滚动。

## 6. 媒体、文本与边界条件

### 媒体规则

- 所有媒体在加载前声明比例，避免累计布局偏移。
- 相册、视频与 GIF 都有明确类型标记；标记文字不能只依赖图标。
- 图片提供替代文本；视频提供字幕入口；GIF 提供暂停；敏感内容提供可理解的遮罩原因。
- 媒体上的文字控件使用自适应深色底，不能直接把白字压在任意照片上。
- 轮播必须支持触控、鼠标、键盘和屏幕阅读器状态播报。

### 文本规则

- 用户名、地点和推荐原因允许单行截断；正文和引用不得横向溢出。
- 中文、英文长单词、URL 和连续 emoji 使用安全换行；不得撑破卡片。
- 推荐、关注、广告、商品、官方和系统提示必须明确区分。
- 计数小于 10,000 显示精确值；更大值使用全产品统一缩写规则，不能一处“1.2万”、另一处“12k”。

### Empty / Restricted / Deleted

- **空流：**解释为什么为空，并提供关注话题、刷新推荐或发布内容中的一个下一步。
- **内容受限：**保留作者和上下文，说明限制原因与可执行操作。
- **内容删除：**在线程中保留关系占位，避免回复失去语境；普通独立卡可从流中移除。
- **未登录：**允许浏览；在用户触发喜欢、收藏、关注或回复时就地说明登录需求，不能预先弹窗阻断。

## 7. 响应式行为

### Wide and desktop

- 发现流使用自适应多列，卡片宽度优先稳定在 220–280px；多出的空间用于列间距和侧栏，不让单卡无限变宽。
- 关注流与详情保持中心阅读轴；侧栏承载话题、创作者或讨论上下文，不承载与当前内容无关的指标。
- Hover 可用，但所有核心功能仍可用键盘和点击完成。

### Tablet

- 侧栏折叠为流内模块或顶部入口，不把它压成窄栏。
- 图集从复杂拼贴降为 2×2 或轮播；动作标签可收缩为图标，但命中区保持。

### Mobile

- 发现流双列只使用 Compact；关系流、讨论、视频播放和详情使用单列 Standard/Detail。
- 底部导航不能覆盖最后一张卡的 Actions；页面底部预留安全区。
- 触控没有 Hover 依赖；长按只用于系统已熟悉的上下文操作，不能替代更多按钮。
- 详情展开尊重安全区、方向切换和软键盘；评论输入出现时不遮住当前回复。

## 8. 可访问性与性能验收

每个卡片类型在进入组件实现前必须通过以下检查：

- 正文与背景对比度 ≥ 4.5:1；大图形和图标状态 ≥ 3:1。
- 所有交互可通过键盘完成，焦点顺序与视觉顺序一致，焦点不被裁切。
- 喜欢、收藏和播放状态同时有形状、文字或可访问名称，不只依赖颜色。
- `prefers-reduced-motion: reduce` 下无位移、缩放、循环 GIF 和 Skeleton 闪烁依赖。
- 媒体懒加载但提前占位；首屏主媒体优先级明确；离屏视频和 GIF 停止解码或播放。
- 360px、760px、1050px、1440px 四个视口完成视觉检查；额外验证超长中文、无图、竖图、横图、九图、长讨论、高互动量、弱网和媒体失败。

## 9. 实现边界

卡片 Pattern 保持框架无关，施工时的 Primitive 首选已确定为 Astryx：

- **Foundation：**颜色、字体、间距、圆角、层级、动效与断点映射为稳定 CSS 变量。
- **Primitive：**按钮、输入、Popover、Dialog、Tabs、Tooltip 等由 Astryx 提供行为与可访问性，通过 LoveCards Theme、公开组件 override 和外层样式定制，禁止修改或 swizzle Core 源码。
- **Community Pattern：**本文的卡片家族、语义顺序、状态连续性和响应式组合由 LoveCards 自己维护；这是品牌差异所在，不能完全交给通用组件默认样式。

组件库升级时，只允许调整 Astryx 版本、主题与少量 Primitive 适配；Foundation Token 与 Card Pattern 的语义契约保持稳定。Astryx 仍为 Beta 且要求 React 19，升级前须通过 `docs/decisions/FRAMEWORK.md` 的门槛；出现 P0/P1 阻塞时再评估 Base UI direct 退路。

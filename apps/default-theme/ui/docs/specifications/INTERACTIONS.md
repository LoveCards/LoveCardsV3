# LoveCards 交互表面规范

> v1.3 · 设计先行冻结。本文约束评论线程、搜索和移动壳层；Dialog、Modal、Alert 和移动 Sheet 的共享结构、焦点与滚动规则见 [`DIALOGS.md`](./DIALOGS.md)，错误翻译与恢复规则见 [`ERROR-FEEDBACK.md`](./ERROR-FEEDBACK.md)。运行实现必须映射到 Astryx 原生组件，不在页面里复制一套“看起来像组件”的 CSS。

## 1. 统一命题

交互要让用户感觉“内容在前，系统随手可用”：信息流保持安静，动作在需要时出现，状态反馈精确而短。评论不是一组松散的白色卡片，而是一条有层级的讨论轨道；搜索不是一条孤立输入框，而是从输入到结果的连续表面；手机端顶部和底部各自承担不同职责，不能重复放置同一入口。

视觉策略为 Restrained：冷中性画布、白色不透明内容面、Deep Rose 只用于当前状态和主要动作。玻璃材质只允许用于媒体上的临时控制，评论、搜索和导航不得默认玻璃化。

## 2. 移动壳层

### 2.1 结构

| 区域 | 规则 | 禁止 |
|---|---|---|
| 顶栏 | 56px；左侧品牌，右侧一个 44px 搜索触发器；滚动时保持稳定 | 顶栏头像与底栏“我的”重复 |
| 搜索面 | 点击触发器打开全屏 Search Dialog；输入框自动聚焦，结果在同一层更新 | 把桌面宽搜索框硬缩到手机 |
| 底栏 | 64px + safe-area；首页、发现、发布、消息、我的五个固定槽位 | 用大悬浮球遮住信息流、把“我的”再放到顶栏 |
| 发布 | 居中主动作但不遮挡文字；44px 命中区 | 只显示图标而没有可读名称/辅助文本 |

消息入口显示真实未读数；加载、空、错误和登录边界都在当前页面内表达。用户中心的唯一稳定入口是底栏“我的”；本人主页身份头的头像可就地更换，内容作者头像仍只承担进入用户主页的身份入口。

### 2.2 桌面壳层

桌面顶栏为 68px：品牌 → 一级导航 → 内联 Typeahead 搜索 → 发布/主题/账号动作。账号动作保留在桌面，手机端不重复。搜索结果层使用 Portal 逃离滚动容器，宽度与输入轴对齐，最多 8 项。

### 2.3 消息与通知

- 收件箱需要登录；检查会话失败显示可重试的错误状态，未登录显示登录动作，不渲染假数据。
- 消息中心的第一入口是 `/messages`。私信列表、会话详情和发送只使用 `messages.conversations/list/send`；`type=message` 通知投影不能替代会话数据。
- 通知二级只保留“互动消息 / 系统通知”。`/inbox` 使用 `notifications.list({ category: 'engagement', cursor, limit })`，`/inbox/system` 使用 `category: 'system'`；旧 `/inbox/message`、`/inbox/social`、`/inbox/interaction` 只重定向到 `/inbox`。
- 通知列表使用 SDK 返回的 `items`、`next_cursor` 和 `has_more`。`next_cursor` 是不透明复合游标，只能原样回传同一 category；禁止解析、构造、跨分类复用或通过多类请求拼接当前页。
- `engagement` 只用于 `NotificationListCategory` 查询。渲染依据 `item.type` 与真实 `item.category`，不得把 `message/social/interaction` 返回项改写成 `interaction`。
- 分类页使用 `notifications.unread({ category: currentCategory })` 与 `notifications.readAll({ category: currentCategory })`；顶部全局角标需要全部通知数时使用不带参数的 `notifications.unread()`。未读总数不得按当前页条目推算。
- 通知流或定时同步必须保留当前 category。若 SDK 快照没有分类能力，只把它作为刷新信号，不能把未筛选条目直接合入当前列表；同步失败时保留手动刷新和错误提示。
- 通知只消费服务端 `action_url`，并继续遵守 `actor_state`、`resource_state` 与站内单斜杠安全校验；不得根据资源 ID 猜路由，也不得在前端解析 `@username` 或创建通知。正文/评论输入中的 `@` 仅用于调用服务端筛选的候选搜索并插入原始文本，通知解析、接收人判定和提及通知仍完全由后端负责。
- 会话列表、会话详情和发送都使用真实消息数据。会话地址无效、消息加载失败、空会话、收件人缺失和发送失败分别表达，不把权限或配置错误显示成“发送成功”。
- 会话列表的视觉语义与信息流保持一致：头像/用户名是身份入口，摘要是独立的会话动作，右侧显示相对时间和真实 `unread_count`。前端优先消费 `last_message_body`、`last_message_at`，缺失时使用明确的“消息内容暂不可见 / 还没有消息，发送第一条”状态，不把原始 SQL 时间戳直接显示给用户。
- 桌面私信列表可以默认展示最近会话；手机列表不把第一条会话伪装成已选择状态，点击后才进入无 BottomNav 的会话任务页。只有 SDK 明确提供的字段才能渲染搜索、在线状态或新建会话动作。
- 私信发送中禁用重复提交；失败保留正文和客户端稳定 ID，允许安全重试。未登录用户只能看到登录边界。

## 3. 信息流卡片动作

- Compact 卡片的底部元数据栏固定为“作者 + 被动喜欢数 + 评论数 + 三点更多”。喜欢数和评论数只提供判断价值，不是按钮。
- 所有卡片表面（首页信息流、完整搜索结果、收藏/历史列表、用户主页动态与详情展开态）复用 `AuthorIdentity`。有效 UID 时，头像与用户名作为同一个链接进入 `/user/{uid}`，身份副文本显示 `UID · {uid}`；无有效 UID、账号已注销或只有展示昵称时保持非链接状态。`@username` 只用于正文/评论提及，不用于账号唯一标识展示。
- 作者身份、卡片正文与更多菜单是彼此独立的交互路径。DOM 中不得出现嵌套链接；点击作者不触发详情，点击正文不触发关注、私信或卡片动作。鼠标、Tab 与 Enter 的结果必须一致。
- 评论与回复使用 `AuthorIdentity variant="comment"`，但必须保留原评论行的视觉语法：32px 头像位于左侧，用户名与时间同处首行，正文和轻量动作沿右侧阅读轴排列；接入主页链接不能增加额外信息行或改变评论密度。
- 私信会话中的用户身份进入主页，会话摘要是独立的摘要操作：桌面用于切换右侧会话面板，移动端进入 `/messages/:conversationId`；两条路径使用兄弟元素，不允许整行链接包裹身份链接。移动端会话是独立任务页，不显示全局 BottomNav。
- 信息流不得直接显示喜欢或收藏按钮。喜欢只在内容详情页执行；收藏、取消收藏、复制链接和举报进入三点菜单。
- 举报自己的内容不显示。服务端没有提供的“不感兴趣”“减少推荐”等能力不得做成看似成功的菜单项。
- 游客可以浏览和复制公开链接；只有在触发收藏或举报时才引导登录，并保留当前返回地址。
- 设计预览和静态蓝图使用同一菜单位置与尺寸，但所有写操作禁用，不得发起 SDK 请求。发布页不渲染信息流卡片预览。
- 菜单触发器与每个菜单项的移动端命中区不小于 44px，支持键盘打开、方向键移动、Esc 关闭和焦点回归。

## 4. 搜索表面

### 4.1 Astryx 映射

- 桌面和移动均使用 `@astryxdesign/core/Typeahead`，不使用手写输入 + 手写下拉。
- 结果项使用 `TypeaheadItem`；图标只表达类型：内容、话题、状态。
- 移动包装为 Astryx `Dialog variant="fullscreen" purpose="info"`，关闭后焦点回到搜索触发器。

### 4.2 状态与时序

1. 空查询：展示最近内容/热门话题；若没有历史，展示“从话题开始探索”。
2. 输入：150–250ms 防抖；中文 IME composition 期间不发请求；新请求取消旧请求。
3. 加载：只在结果层显示局部 Skeleton，不让整页跳动。
4. 有结果：类型 → 标题 → 作者/话题上下文；Enter 打开高亮项，方向键移动，Esc 关闭。
5. 无结果：保留输入，提示“换个关键词试试”，提供进入完整搜索页的动作。
6. 错误：结果层内联显示重试；不把错误变成空白页。

### 4.3 页面搜索与顶栏搜索

顶栏搜索是快速进入内容/话题的入口；发现页搜索是可持续编辑的查询表面。二者共享同一 `SearchSource` 和结果语义，但发现页保留 URL `q`、范围 Tabs 和完整结果流。不得出现两个不同的结果排序或不同的“搜索中”文案。

## 5. 评论线程与回复

### 5.1 信息结构

评论区是一条 `CommentThread`：

```text
讨论标题 / 数量
└─ RootComment
   ├─ ReplyComment
   └─ ReplyComment
└─ RootComment
Composer（新评论或回复）
```

- Root 评论与回复使用同一行语法，不使用每条评论一张卡片。
- Root 行：头像 32px、作者/时间、正文、轻量动作；回复缩进 20px，左侧只用 1px 分隔线，不做彩色粗侧条。
- 只有存在回复时才显示“2 条回复”；默认展示首层和最多 3 条回复，更多回复进入同页展开，不跳到黑色中转页。
- 删除评论保留“原评论已删除”的关系占位，避免回复失去上下文。

### 5.2 Composer

- 使用 Astryx `ChatComposer` + `ChatComposerInput` + `ChatSendButton`，`elevation="none"`，内容面与详情同源。
- 新评论 placeholder：“写下你的回复”；回复状态显示 `回复 @用户名` 和 44px 取消按钮。
- Enter 发送，Shift+Enter 换行；IME 组合期间 Enter 不发送；发送中保留内容并禁用重复提交。
- 错误显示在 composer 下方，输入内容不清空；成功后清空并把焦点留在 composer。
- 右侧显示“已回复 / 140”计数，达到限制时仅禁用发送，不截断用户文本；与当前后端评论校验保持一致。

#### 5.2.1 @ 提及

- 卡片正文、根评论和回复共用 Astryx `ChatComposerInput` 的 `@` trigger；输入 `@` 后继续键入至少一个字符，候选菜单在光标附近打开。桌面使用 Portal 定位，窄屏保持同一输入轴内的可滚动菜单，不新增路由。
- 候选只来自生成 SDK 的 `users.searchMentionCandidates({ query, limit })`；服务端负责 active、删除、主页可见性、双向屏蔽和当前用户过滤。SDK 未提供该能力或网络失败时，输入仍可按普通文本提交，不显示伪造用户或阻塞发布。
- 鼠标点击、ArrowUp/ArrowDown、Enter/Tab 选择结果后插入 `@username ` 原始文本；不插入 user_id、不可见 token 或前端通知数据。Esc 关闭菜单，Shift+Enter 保留换行，IME 组字期间不触发提交。
- 空查询不枚举用户；无结果显示可继续按普通文本发布的非阻塞提示。候选头像与用户名共用现有 Avatar、颜色和圆角 token，不引入第二套视觉语言。
- 视觉语义上，候选项默认保持中性，`@username` 使用主题强调色（`--lc-rose-deep`），不使用错误红；鼠标悬停、键盘选中和 `aria-selected` 使用低对比度主题底色与清晰的文字强调。只有无效查询、请求失败等真实错误才使用 danger 色。
- 已发布内容的卡片正文、评论和回复统一使用 `MentionText` 展示器；它只消费服务端返回的结构化 `mentions` 区间和站内 `action_url`。没有该字段、区间非法或用户不可用时降级为原始文本，不通过正则猜测用户链接。
- 发布和评论提交继续把完整原始正文交给现有 SDK；后端 `MentionParser/Mentions` 决定是否有效、去重、排除本人/屏蔽用户并生成通知。前端不得解析正文来决定收件人。

### 5.3 SDK 边界

当前 SDK 已有 `comments.cardList`、`comments.create(parent_id)`、编辑和删除，因此回复可真实接入。`parent_id` 必须属于当前卡片；若后端未验证，前端仍只发送当前卡片内已读到的 ID，并在后端契约中列为必须补齐的归属校验。

### 5.4 作者置顶评论

- 只有卡片作者可管理自己卡片的置顶评论；首期只允许真实一级评论（`parent_id === null`），回复及父评论缺失的孤儿回复都不能置顶。
- 一级评论右上角三点菜单按“复制评论 → 置顶评论/取消置顶 → 删除评论（仅评论本人）”组织。菜单项在请求中禁用；一张卡片只有一个置顶位。选择新评论且已有另一条置顶时，用一次确认弹窗说明将替换旧项；取消当前置顶不额外确认。
- `is_pinned`、置顶排序和替换结果完全以服务端响应为准。前端不乐观翻转角标，写入成功并重新加载评论后才显示 Toast。
- 默认主题只调用生成 SDK 的用户侧能力。管理端 `pinManaged/unpinManaged`、手写 URL 或在 SDK 未就绪时展示假成功入口均被禁止。
- SDK 未提供用户侧置顶方法与 capability 前，组件只保留可测试的动作边界，正式页面不显示置顶项。

## 6. 当前互动范围

当前产品只登记普通评论线程，不提供投票卡片、单选规则或基于评论 marker 的兼容协议。`discussion` 是普通内容类型：信息流展示标题与正文，详情页使用同一 `CommentThread` 承载根评论和回复。

- 历史或未知互动声明不能生成操作控件，也不能改变卡片类型、权限或资源归属。
- 评论必须按普通正文显示、编辑和删除；前端不再把任何评论解释为协议事件。
- 若未来重新评估结构化互动，必须先完成独立产品决策、后端资源契约、SDK 能力和新的设计验收，不能复用当前评论正文作为事件存储。

## 7. 交互验收矩阵

| 表面 | 桌面 | 手机 | 键盘/读屏 | 无 API |
|---|---|---|---|---|
| 搜索 | 原位 Typeahead | 全屏 Dialog | 方向键、Enter、Esc、焦点回归 | 显示配置错误，不显示假结果 |
| 评论 | 单列线程 + 内联 composer | 同结构，空间不足时转 Sheet | Tab、Enter/Shift+Enter、IME | 登录提示，保留正文 |
| 移动壳 | 不适用 | 顶部搜索、底部我的唯一入口 | 每项 44px | 真实未读、空、错误、登录状态 |
| 卡片作者 | 头像/用户名同一 UID 主页链接 | 连续命中区且不覆盖正文 | Tab、Enter、清晰 Focus Visible | 无有效 UID 时保持普通文本 |

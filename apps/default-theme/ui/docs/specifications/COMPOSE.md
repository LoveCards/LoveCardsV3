# 发布器与草稿交互规范

## 内容形态

发布页先由用户显式选择内容形态，再根据所选类型校验媒体：

- `随笔`：纯文字，隐藏媒体工作区，正文必填。
- `图文`：1–9 张 JPEG、PNG、WebP 或 GIF；一张写入 `image`，多张写入 `gallery`。媒体上传区先出现，正文紧随其后且必填。
- `视频`：一个 MP4、WebM、MOV 或 M4V 文件，写入 `video`。媒体上传区先出现，正文紧随其后且必填。

普通 Card 只有一个可编辑的 `content` 正文字段，不提供标题。正文最多 1000 字；随笔、图文和视频使用同一限制。800 字后显示剩余字数，超过上限属于字段错误且不能发布。长文不通过 `data.title` 或放宽 Card 正文模拟，未来使用独立内容模型与编辑器。

`image` 与 `gallery` 是“图文”这一用户类型的两种数据状态，不拆成两个发布入口。类型选择使用单选分段控件并支持方向键；没有文件上传权限时保留“随笔”，图文与视频明确禁用。

## 页面结构

发布页不是三步向导，也不是信息流卡片预览器。桌面与手机共用一条连续编辑轴，语义顺序固定为：

1. 局部页面头：返回/取消、标题、草稿箱。
2. 发布类型分段控件。
3. 条件媒体区；随笔隐藏，图文或视频显示。
4. 正文；随笔直接出现，图文或视频固定放在媒体区下方并且必填。
5. 话题与卡片可见范围。
6. 当前任务反馈。
7. 保存状态、取消、存入/更新草稿、确认发布。

桌面使用 `editor` 容器，编辑轴最大 860px；不设置左侧伪步骤栏，也不设置重复字段状态的“发布检查”侧栏。Section 通过间距和分隔线组织，只允许最外层编辑表面使用 `--lc-radius-panel`。手机隐藏产品顶栏，使用局部任务顶栏；页面内容保持 12–16px gutter，固定动作栏位于产品 BottomNav 与 safe-area 之上。

发布主动作只有“确认发布”。“存入草稿箱 / 更新草稿”是次动作，“取消”在桌面 Footer 与手机局部顶栏可达。发布页不重复展示当前账号身份，也不在状态区重复所选内容类型；账号可在产品顶栏确认，类型可在分段控件确认。唯一常驻的任务信息是保存状态，并与草稿动作相邻显示“尚未存入草稿箱 / 有未保存的修改 / 正在保存 / 已保存到草稿箱”。无内容且未开始编辑时不占据额外一行。保存或发布过程中按钮保持原尺寸，禁止重复提交。

## 卡片可见范围

卡片范围使用与发布类型一致的单选分段控件，提供 `公开 / 仅关注者 / 仅自己` 三项，并直接提交生成 SDK 的 `CardVisibility`：

- `public`：前端显示“公开”，新发布默认选中并显式提交。
- `followers`：前端只表达用户选择，不查询关注关系，也不推算最终访问者。
- `private`：前端显示“仅自己”，最终权限仍由服务端执行。

卡片范围会与账号 `profile_visibility` 取交集，说明文字必须明确这一点。首页、搜索、关注流、用户主页、收藏、喜欢、历史与详情只消费服务端过滤后的卡片和 `Card.visibility`；不得根据关注关系、接口失败或媒体 URL 推断访问权限。

编辑已发布卡片时从 `cards.getOwn()` 返回的 `Card.visibility` 回填；范围未修改时 PATCH 不提交 `visibility`，修改时必须提交当前值，包括从 `followers/private` 改回 `public`。草稿将范围保存在 `payload.visibility`，旧草稿缺失或值无效时按 `public` 恢复。

## 校验与反馈

- 正文为空、话题超过 3 个、媒体缺失、文件类型/体积/数量不符属于字段或媒体区错误；错误紧贴对应控件并关联 `aria-describedby`。
- 提交时按“正文 → 媒体 → 话题”定位第一个错误。未尝试提交前不提前把空必填项标红。
- 网络、权限、登录或服务端失败影响整个保存/发布任务，使用编辑器内 scoped Banner；错误必须说明当前输入已保留以及可执行的下一步。
- 正常保存/发布成功使用 Toast 或原位状态，不额外堆叠成功 Banner。发布后跳转到正式详情。
- 恢复草稿时保留页面头、编辑器宽度和字段节奏，只将数据轨道替换为对应 Skeleton；不得伪造作者行、保存状态或使用通用 Spinner、无关灰卡。

## 媒体上传

上传区是编辑器的一部分，不使用大面积空白拖放框，也不在 `FileInput` 后重复渲染第二个“添加媒体”空态。空状态使用紧凑 FileInput，显示加号、明确动作和人类可读限制；选择后显示有序缩略图、序号、移除操作和媒体数量。失败时保留已选文件，允许重新提交。

文件的类型、体积、数量和损坏属于 FileInput/文件项状态；网络、权限和整个上传任务失败属于发布工作区的 scoped Banner。多文件中单项失败不能清空其他已完成文件。完整规则见 [`FORMS-AND-UPLOADS.md`](./FORMS-AND-UPLOADS.md) 和 [`FEEDBACK-AND-STATUS.md`](./FEEDBACK-AND-STATUS.md)。

切换到与已选媒体不兼容的类型时，使用确认弹窗说明“正文和话题保留、媒体将移除”。没有媒体时立即切换，不额外打断。视频不生成图片封面字段；媒体 URL 与文件 ID 继续通过卡片媒体字段保持归属和顺序。

发布页不提供信息流实时预览。媒体区只显示本地上传缩略图，用于确认顺序、识别文件和移除媒体；它不是最终卡片模拟。发布后的正式呈现统一由信息流 `FeedStory` 和详情媒体组件负责，发布页不得维护第二套卡片表现。

## 已发布内容编辑

已发布卡片不在详情页内嵌一块缩水输入框。作者从详情菜单选择“编辑内容”后进入 `/compose?edit=<cardId>`，继续使用与发布、草稿恢复相同的完整编辑轴；加载必须调用 SDK `cards.getOwn(id)`，不能用公开详情代替归属校验。

- 编辑器恢复 `content`、全部 `topics[].name`、`data.kind`、`visibility`、有序 `media[]` 与未被当前界面编辑的扩展 `data`。数字 `tags` 只用于关系标识，不能显示成 `#13` 一类伪话题名。
- 编辑模式标题为“编辑内容”，说明“修改会直接更新这张卡片”，主动作是“保存修改”；返回与取消回到 `/post/<cardId>`。
- 编辑模式不显示草稿箱入口，也不提供“存入草稿箱 / 更新草稿”。保存只调用 `cards.update`，不得创建或删除草稿。
- 仅修改正文或话题时不重绑媒体；只有新增、移除或切换媒体形态时才提交完整有序 `media_file_ids`。更新失败清理本次新上传文件，但保留原媒体和页面输入；成功后才清理用户明确移除的旧媒体。
- `draft` 与 `edit` 同时存在、无效 ID、加载中、404、403 和网络失败分别表达，禁止静默选择一种模式或把权限错误伪装成不存在。
- 离开有未保存修改的编辑器继续使用统一确认弹窗；Skeleton 与发布器最终字段轴一致。

## 草稿箱

草稿是发布页编辑状态的保存结果，不是独立的内容类型，也不是另一套编辑器。

- 只有发布页的“存入草稿箱”动作会创建草稿；打开发布页、输入内容或进入草稿箱都不会自动创建空草稿。
- 草稿不提供用户填写的标题。列表展示名由正文第一行派生；没有正文时显示内容类型，例如“视频草稿”。后端兼容字段 `title` 只保存这个派生值，不是可编辑产品字段。
- 草稿箱只展示未发布内容。点击列表项统一返回 `/compose?draft=<id>`，发布页恢复同一套类型、正文、话题和媒体字段。
- 新草稿使用“存入草稿箱”，已有草稿使用“更新草稿”；保存失败时保留当前页面输入，不清空本地文件或已恢复媒体。
- 保存媒体草稿时，媒体先上传并以有序引用写入草稿 payload；`visibility` 与类型、话题一起保存，旧草稿缺失时恢复为 `public`。恢复发布时复用这些文件，不重复上传。用户移除媒体或删除草稿后清理仍未被正式内容引用的上传文件。
- 发布成功后删除草稿记录，保留正式卡片正在使用的媒体引用。

草稿箱是发布任务的二级恢复页面，使用最大 860px 的 `editor` 单轴，不设置统计侧栏，也不展示没有服务端依据的“云端同步正常”。桌面保留产品顶栏和局部返回；手机隐藏产品顶栏与 BottomNav，使用“返回 / 草稿箱 / 发布”局部顶栏。

草稿列表是一张连续表面：顶部只说明“最近编辑”和排序规则；每行依次展示首个真实媒体缩略图（无媒体时按内容类型回退）、派生标题、一行不重复标题的摘要、内容类型与人类可读更新时间。点击主要内容恢复编辑，删除是独立的同级按钮，禁止把按钮嵌入恢复链接。手机端列表取消外层悬浮卡圆角，保留页面 gutter、行分隔线以及 44px 触控目标。

加载 Skeleton 必须与最终行的缩略图、文本轨道和操作位同高；列表加载失败提供原位重试，删除失败使用列表上方 scoped Banner，删除成功使用短 Toast。空列表只解释“草稿由发布页主动保存”，并提供“发布新内容”动作。

## 评论

评论采用单一连续讨论流：回复上下文紧贴输入框，输入框支持多行、字数计数、发送中禁用、失败保留草稿；评论行使用紧凑分隔，不为每条评论创建松散独立卡片。完整的线程、回复、失败和登录状态规则见 [`INTERACTIONS.md`](./INTERACTIONS.md)。

## 组件复用

施工时优先复用 Astryx 原生能力：`SegmentedControl` 负责发布类型和卡片可见范围，紧凑 `MediaDropzone` 基于 `FileInput` 负责选择、拖放、类型和数量校验，`ChatComposerInput` 负责正文、多行和 `@` 提及触发，`Typeahead` / Tokenizer Pattern 负责最多 3 个话题，`ScopedBanner` 负责任务失败，`Dialog` 只用于切换类型与放弃未保存内容的确认。LoveCards 只覆盖布局、Token 和状态样式，不复制底层行为组件。

正文中的 `@` 只通过生成 SDK 的 `users.searchMentionCandidates` 获取经服务端筛选的候选；选择后写回 `@username ` 原始文本，发布请求仍提交原始 `content`，不提交 `mentioned_user_ids`，也不在前端生成通知。

## 响应式验收

- 320、390、768、1050 与 1440px 无横向滚动、动作遮挡或控件压缩。
- 手机正文、媒体、话题与最终状态保持同一 12–16px 内容轴；固定动作栏不覆盖最后一个字段，软键盘关闭后恢复原位置。
- 分段控件、媒体动作、话题移除和所有 Footer 动作触控目标至少 44×44px；Tab、Enter、Space 和方向键路径完整。
- 深浅主题只使用语义 Token；面板、媒体、字段和控件分别使用 14/12/10/9px 语义圆角，不写页面私有近似值。
- 长错误、1000 字正文、9 张媒体、3 个长话题、无头像与超长用户名均不破坏布局。

# 重构纪律

## 核心规则

1. 先证明当前行为，再改变结构。
2. 每次只处理一个垂直切片，避免按“Controller 全部改完、Service 全部改完”横向迁移。
3. 结构变化与行为变化分开提交。
4. 新依赖必须符合架构约束表；已知债务只能减少。
5. 过渡代码必须有明确删除条件，不能成为永久双轨。
6. 一处改动带来的复用必须来自稳定概念，不为未来猜测提前抽象。

## 单次重构流程

1. **定义边界**：写清入口、输出、持久化、副作用和不在范围内的内容。
2. **建立基线**：补特征测试或保存可重复的 API/构建验证命令。
3. **画出依赖**：列出现有调用者、被调用者和跨层依赖。
4. **选择一个接缝**：先提取契约或上下文对象，不同时搬迁全部实现。
5. **切换一个调用者**：验证通过后再继续下一个。
6. **删除旧路径**：没有调用者后立即删除，不保留“以防万一”的实现。
7. **固化规则**：更新架构检查、文档和模块模板。

## 完成定义

- 对外行为与基线一致，或行为变化已被明确批准。
- 旧实现、无效 import 和临时兼容路径已移除。
- 自动架构检查和受影响测试通过。
- 文档中的职责与真实代码一致。
- Diff 中每一行都能追溯到本次目标。

# 管理端信息架构与 UX 设计基线

> 状态：2026-09-14 信息架构收敛已确认；应用壳与标签样板进入施工
>
> 日期：2026-08-23
>
> 范围：整个 `apps/admin` 管理端的导航、角色视图、页面层级、页面模板、状态语言和分阶段迁移策略。
>
> 本文件定义产品与交互基线；对应导航、页面壳、角色可见性和错误状态已在 `apps/admin` 落地，旧路径继续作为兼容入口。

## 1. 设计结论

LoveCards 管理端应从“按技术模块堆放的页面集合”改成“按角色和任务组织的工作台”。技术保持 Nuxt + Vuetify；优先重做信息架构和统一页面壳，再逐域迁移旧页面。

本次锁定为一个一级直达入口和四个任务组：

1. 工作台
2. 内容与社区
3. 用户与权限
4. 系统设置
5. 系统运维

工作台直接进入个人任务上下文；四个任务组只负责发现页面。具体资源、驱动、测试、迁移和高风险动作下沉到详情或子流程。

视觉参考图已放在 [admin-ui-reference](assets/admin-ui-reference/README.md)。它们用于统一页面层级、密度和状态表达；最终导航、文案和权限仍以本文件与角色矩阵为准。

## 2. 为什么需要重构

当前导航在 `config/navigation.ts` 中有一个总览和多个平铺分组，内容、治理、安全、运维和配置边界互相穿插。[当前导航清单](../../apps/admin/config/navigation.ts)

当前布局只提供抽屉和页面插槽，缺少统一的页面上下文、面包屑和详情层级。[当前布局](../../apps/admin/layouts/default.vue)

现有共享组件已经定义了 `AdminPageHeader`、`AdminAsyncState`、`AdminStatusChip` 和危险操作组件，但旧 CRUD 页面没有统一使用，形成“新页面规范”和“旧页面规范”两套体验。[管理端架构约束](ADMIN-ARCHITECTURE.md)

权限设计曾存在可见目录和实际接口不一致的情况。当前边界已经拆分：普通用户无评论正文编辑路由，后台使用 `comments.update.all` 修正正文，评论审核和卡片级置顶分别使用 `comments.moderate.all` 与 `comments.pin.all`。[权限边界基线](../../apps/backend/tests/Authorization/PermissionBoundaryBaseline.php)

因此本次问题的根因不是 Vuetify，而是：

- 信息架构按实现模块而不是任务域组织；
- 页面层级没有统一的“域 → 资源 → 详情/配置”模型；
- 角色、导航可见性、动作权限和数据范围没有被同一份契约驱动；
- 列表、配置、错误、危险操作和审计反馈没有统一组件语法。

## 3. 角色与使用场景

“超级管理员”和“管理员”继续作为兼容角色；系统同时正式提供内容运营、社区运营、审核员、安全管理员、运维管理员和审计员六个稳定角色模板。模板通过幂等种子创建，但不会自动给现有账号分配新角色。

| 角色模板 | 主要目标 | 默认工作台内容 | 默认高风险边界 |
| --- | --- | --- | --- |
| 超级管理员 | 了解全局并处理任何异常 | 全部待办、全系统健康、最近变更、权限入口 | 无默认隐藏项，但每个危险动作仍需二次确认和审计 |
| 管理员 | 完成日常站点管理 | 内容、社区、用户待办及关键健康摘要 | RBAC、升级、密钥和恢复等能力按 grant 显式开放 |
| 内容运营 | 管理内容质量和分类 | 待处理卡片、评论、标签、内容趋势 | 不接触账号恢复、系统密钥和升级 |
| 社区运营 | 处理社区秩序和反馈 | 举报队列、评论治理、社区洞察 | 不修改站点基础设施 |
| 审核员 | 快速完成审核判断 | 待审核/举报队列、证据上下文、处理历史 | 只可执行被授予的审核动作；不可编辑评论正文 |
| 安全管理员 | 处理账号风险 | 恢复申请、会话风险、用户安全事件 | 敏感字段最小可见；所有撤销操作要求原因 |
| 运维管理员 | 保证服务可用和可恢复 | Worker/SSE/存储/通知投递/升级状态 | 不默认读取用户内容和 RBAC |
| 审计员 | 还原“谁何时改变了什么” | 审计、异常和只读治理记录 | 全部动作只读 |

角色视图必须由 capability 和数据范围共同决定。不能仅根据角色名称在前端写死页面。

## 4. 目标信息架构

```text
工作台
├─ 我的待办
├─ 系统健康
└─ 最近变更

内容与社区
├─ 卡片
├─ 评论
├─ 标签
├─ 文件管理
├─ 举报处理
└─ 社区洞察

用户与权限
├─ 用户管理
├─ 账号恢复记录
├─ 角色
├─ 权限目录
└─ 用户详情
   ├─ 概览
   ├─ 安全会话
   └─ 审计记录

系统设置
├─ 站点与社区规则
├─ 主题外观
├─ 存储配置
├─ 消息渠道
└─ 验证

系统运维
├─ 运行状态
├─ 通知投递
├─ 升级与迁移
└─ 审计日志

```

### 4.1 页面层级规则

- 一级：工作台直达和四个任务组。
- 二级：资源列表或配置入口，例如“内容与社区 → 卡片”。
- 三级：资源详情、驱动详情、主题 schema、迁移步骤、投递详情和测试工具。
- 侧栏不渲染无独立页面的中间分区标题；初次进入只展开当前任务组。
- 详情页不在侧栏重复出现，统一由面包屑和父页面返回。
- 旧地址继续保留兼容跳转；新导航不暴露旧拼写或技术路径。

### 4.2 建议的规范路由命名

以下是设计阶段的规范命名，施工时可以保留现有 URL 作为 alias：

| 域 | 规范入口 | 详情/子流程 |
| --- | --- | --- |
| 工作台 | `/apps/dashboard` | 待办和健康区块通过 query 或局部链接进入域页面 |
| 内容与社区 | `/apps/content/cards`、`/apps/content/comments`、`/apps/content/tags` | `/apps/content/*/:id` |
| 社区治理 | `/apps/community/reports`、`/apps/community/insights` | `/apps/community/reports/:id` |
| 用户与权限 | `/apps/users`、`/apps/security/recovery`、`/apps/access/roles`、`/apps/access/permissions` | 用户、角色和权限详情 |
| 系统设置 | `/apps/settings/site`、`/apps/settings/community-rules`、`/apps/settings/appearance`、`/apps/settings/storage`、`/apps/settings/messaging`、`/apps/settings/verification` | 主题与渠道详情/测试 |
| 系统运维 | `/apps/operations/runtime`、`/apps/operations/deliveries`、`/apps/operations/audit` | `/apps/operations/upgrade`、投递/审计详情 |

施工时必须先建立旧地址到规范地址的映射表，不能直接删除现有链接。

## 5. 角色化工作台设计

首页采用“待办优先 + 健康摘要”，不做装饰性数据大屏。

### 5.1 固定骨架

1. 顶部上下文栏：产品名、环境（local/staging/production）、当前角色、全局搜索、最近操作和退出。
2. 主列“我的待办”：按优先级、积压时间和风险排序；每项必须能直接进入处理页。
3. 侧列“系统健康”：只显示当前角色有权看到的设施和聚合状态。
4. 底部“最近变更”：展示操作者、资源、时间、结果和审计链接。
5. 快捷操作：只显示当前角色有权执行且常用的动作。

### 5.2 各角色的默认区块

- 超级管理员：举报、审核、恢复、失败投递、Worker/SSE、数据库/存储、最近升级和权限变更。
- 管理员：内容和社区待办、账号异常摘要、通知失败摘要；高风险系统操作只显示入口状态，不默认给操作权。
- 内容运营：待审核卡片、隐藏/恢复内容、标签待整理、内容趋势。
- 社区运营：举报队列、评论治理、互动趋势和近期处理结果。
- 审核员：只显示可处理队列、证据快照和处理历史。
- 安全管理员：恢复申请、Session 风险、账号状态变更和安全审计。
- 运维管理员：运行设施、投递积压、存储容量、升级/迁移状态。
- 审计员：审计检索、失败操作和只读资源快照。

### 5.3 统计卡片的使用限制

统计只用于回答“是否需要行动”。每个指标必须同时提供：来源、时间范围、更新时间、点击后的列表和失败状态。没有数据与请求失败不能都显示为 0。

## 6. 统一页面语法

### 6.1 列表页

```text
Breadcrumbs
PageHeader：标题 / 用途说明 / 一个主动作
ContextStrip：待办数、同步时间或降级提示（可选）
FilterToolbar：搜索、常用筛选、保存视图、重置
ResultBar：结果数、排序、列设置
ResourceTable：核心列、状态、行操作菜单
Pagination
```

规则：

- 默认只显示支持当前任务的 5–8 个核心列。
- 技术字段进入详情的“诊断信息”，不占用主表格宽度。
- 批量动作必须按动作 capability 独立过滤，不用一个粗粒度 guard 包住所有选项。
- 搜索、筛选、排序和分页写入 URL，刷新或分享链接后状态可恢复。
- 首次空、过滤无结果、无权限、错误和降级使用不同文案与操作。

### 6.2 详情页

```text
Breadcrumbs
ResourceIdentity：名称/handle、类型、当前状态
PrimaryAction：当前角色最可能执行的一个动作
Summary：关键字段和权限范围
Tabs：概览 / 内容或安全 / 历史
AuditTimeline：操作者、原因、前后状态、时间、request/correlation id
```

### 6.3 配置页

配置按“基础 → 业务 → 高级”分区，不把所有字段放在同一张卡片或同一个 tab 中。

- 保存范围必须写在保存按钮附近。
- 有未保存变更时显示 dirty 状态和离开提示。
- 字段错误就地显示；服务端错误保留原值并给出重试入口。
- 驱动、渠道、主题和验证器采用“列表 → 详情 → 测试”三级流。
- 高风险变更显示影响范围、当前值/新值、审计原因和回滚说明。

### 6.4 统一状态词汇

| 状态类 | 文案示例 | 必备信息 |
| --- | --- | --- |
| 加载中 | 正在加载卡片 | 骨架，不用页面中央旋转圈掩盖结构 |
| 空数据 | 当前筛选下没有卡片 | 清除筛选或创建入口 |
| 无权限 | 你没有查看此页面的权限 | 所需职责/返回工作台 |
| 网络/服务错误 | 暂时无法读取卡片 | 重试、错误编号、是否可能已执行 |
| 降级 | 实时状态不可用，显示最近一次同步 | 时间戳和恢复提示 |
| 成功 | 已隐藏 3 条卡片 | 影响数量、审计链接、撤销/后续动作 |

所有状态同时使用文字、图标和颜色。现有 Indigo、Roboto、平面内容表面和 4–12px 圆角继续沿用 `apps/admin/DESIGN.md`。

## 7. 权限、内容和审计契约

导航契约必须至少包含：

```text
domain
route
required_capabilities
action_capabilities
data_scope
risk_level
```

权限体验分为四层：

1. 导航可见性：没有入口就不显示分组和徽标。
2. 页面读取：进入页面前给出明确的 403 状态。
3. 动作权限：每个编辑、审核、删除、重试、升级动作单独判断。
4. 数据范围：同一页面根据 global/resource/self scope 过滤数据和字段。

后端始终是最终安全边界；前端隐藏按钮不能代替后端授权。

固定业务边界：

- 卡片可以在被授权时编辑。
- 普通用户不提供评论正文编辑动作；后台拥有 `comments.update.all` 的管理员可在填写审计原因后修正正文，审核、隐藏、恢复和删除仍使用各自能力。
- 私密、草稿、已删除和受限资源显示资源状态占位，不泄露正文。
- 所有危险动作写入审计；确认弹窗必须包含资源、影响和可恢复性说明，并以明确动作按钮完成确认。可恢复性不同的同类操作（如回收站删除与永久删除）必须在文案上区分后果；确认弹窗不要求输入文字（见 ADMIN-ARCHITECTURE 危险操作确认规范）。

## 8. 已落地的施工契约

以下四份契约已经与后端边界共同落地，并继续作为后续页面的准入条件：

1. **路由地图**：规范路径、旧路径 alias、页面级 capability、详情入口。
2. **角色矩阵**：角色模板 × 域 × 读取/动作/数据范围；标出当前已存在和未来待启用的 grant。
3. **状态目录**：资源状态、错误码、降级状态、空态和危险操作文案。
4. **组件清单**：页面壳、列表工具栏、表格、详情、配置分区、状态、确认和审计组件。

任何页面只有在这四份契约中有位置后才能开始迁移。

## 9. 分阶段施工记录

### Phase 0：契约准备

- 固化导航域、路由 alias 和 capability 映射。
- 清理过期能力展示，并确保评论编辑、审核、置顶能力分别展示。

- 侧栏二级分组、当前域展开和权限过滤。
- 顶部环境/角色上下文、全局面包屑和统一页面容器。
- 角色化工作台和真实 loading/error/empty 状态。

### Phase 2：共享页面模板（已完成）

- `AdminPageHeader`、`AdminAsyncState`、`AdminResourceTable`、`AdminFilterToolbar`、`AdminConfigSection`、`AdminDangerActionDialog`、`AdminAuditTimeline`。
- 统一通知、错误、分页、列设置和 URL 状态同步。

### Phase 3：按域迁移页面（已完成）

1. 用户与安全、举报和通知投递。
2. 系统配置、存储、发信和验证。
3. 评论、标签、角色、权限。

### Phase 4：验证（已完成）

- 每个角色的导航和页面 E2E。
- 每个高风险动作的 403、前置状态、审计和失败恢复测试。
- 桌面、窄屏、键盘、缩放和减少动态效果检查。

## 10. 完成判定

本轮实现按以下条件验收：

- 每个现有页面都能归入一个一级域和一个二级任务。
- 每个详情/配置页面都有父级入口和面包屑。
- 每个角色都有明确的首页区块和数据范围。
- 每个页面动作都有对应 capability 和后端 route。
- 评论不可编辑、卡片可编辑等业务边界在 UI 文案和权限目录中一致。
- 所有列表和配置页面的状态、错误、空态和审计反馈已经定义。
- 旧 URL 的兼容策略已经列入路由地图。

以上条件已经转化为导航契约、共享组件、后端授权与审计测试、SDK 契约和管理端 E2E；后续新增管理页面仍必须遵守同一基线。

# 通信管理三页重设计（2026-11-07）

> 本文保留三页信息架构和当时的验收记录。2026-11-10 起，实时故障不自动切轮询；模式、健康、主动提示目录与 Redis 配置遵循 [FRONTEND-SIGNALS.md](FRONTEND-SIGNALS.md)。以下涉及自动降级的旧示例不再作为当前行为要求。

## 目标与边界

目标是让管理员按顺序回答三个问题：**现在能否正常通信、事件为何没有形成通知、哪些通知允许生成**。保留现有 Vuetify 外壳、权限、SDK 请求边界和服务端裁决；页面不读取私信正文或 Outbox payload，不把浏览器模式与通知生成混为一谈。

本方案已在当前工作树实现：三页与投递详情、通知队列汇总和策略事件名的向前迁移均已编写。代码已同步到原 dev 工作树；验收入口是 `http://45.207.204.11:20089/admin/`，API 是原 `6001` 服务。云端 `npm run check` 已通过；浏览器及隔离库 E2E 验收结果以本轮最终验收记录为准，不以旧独立预览入口的结果代替。

### 管理员需要理解的一条链

```text
业务事实 → Outbox 事件 → 事件处理器 → 策略判断 → 用户通知记录
   │                                               │
   └─ 私信等业务数据已提交 ──────────────────────────┤
                                                   ↓
                              浏览器通过轮询或 Gateway 刷新数据
```

- **运行状态**：检查链路及浏览器通信方式是否可用；轮询和实时只影响浏览器何时获知新内容，不决定业务事件是否发生。
- **通知投递**：检查事件处理器有没有处理成功、失败或按策略跳过。这里的“投递”不是用户已读、也不是浏览器已经收到。
- **通知策略**：控制指定事件是否生成站内通知。关闭 `message.sent` 的通知投影不阻止私信写入，也不阻止私信列表刷新；系统安全与审核通知不可关闭。

三页保留独立导航，页首用一行文字与相邻页的链接表达这条关系，不另建总览大屏。

## 已确认的阻断问题

### P0：三个策略开关无法匹配实际事件（已修，dev 迁移已应用）

`20261106000006.sql` 的种子和版本快照使用 `content.saved`、`comment.published`、`mentions.added`；`HandlerRegistry` 与发布端实际使用 `library.saved`、`content.comment.published`、`content.mentions.added`。`NotificationPolicyGate::decide()` 按事件名精确查版本快照，找不到时返回 `not-configured` 并继续创建通知。因此这三个开关可能“保存成功，但仍发通知”。当前使用向前迁移生成新的策略版本；历史版本与已登记投递的冻结语义不回写。隔离库与部署验收须明确查询当前版本的七个事件名和三个规范名；迁移 SQL 的 `verify` 阶段只执行查询，不能把查询返回计数当成自动断言。

### P1：投递页没有展示策略处理结果（已实现）

`event_deliveries` 已有 `policy_revision` / `policy_decision`，但 `AdminReadModel::deliveries/delivery`、`AdminDeliveryResource` 和 SDK 类型未返回。`status=completed` 可能代表通知已创建，也可能代表按策略跳过；目前 UI 无法区分。补只读字段并显示“已按策略跳过 / 已执行投影 / 旧记录未配置”，不要把 `completed` 一律翻译为“用户收到通知”。

### P1：通知投递页混用了两种统计口径（已实现）

页首的“通知总量、未读通知、覆盖用户”来自 `notifications` 全库；列表来自 `event_deliveries` 全部队列，包含非通知任务（例如文件清理）。数字不能解释下方记录。把用户通知总量移到独立的业务统计位置；本页默认只看 `queue_name=notifications`，聚合只统计同一队列、同一时间窗的处理结果。现有列表 API 尚无 `queue_name` 筛选和专用汇总，需要补后端契约，不能在当前页数据上前端假过滤或推算总数。

### P2：详情页把推断写成了时序事实（已实现）

现有详情用 `created_at`、`available_at`、`updated_at` 拼出“投递时序”；`available_at` 只是可执行时间，`updated_at` 不是一次准确的尝试记录。首版改为“记录时间 / 可执行时间 / 最近更新”和“当前状态 / 尝试次数 / 最后错误”，不画伪时间轴。只有后端提供持久化 attempts 后才增加逐次时间轴。

## 一、运行状态：先判断是否需要处理

### 首屏结构

```text
运行状态                                        [刷新]
当前通信：正常 · 浏览器通过轮询更新              最近检查时间
说明：新私信和通知会按所设间隔刷新。             [查看通知处理]

需处理的问题（仅异常时出现）
  例：已选实时，但 Gateway 不可用；主动更新暂停，浏览器显示同步异常。
  原因、受影响范围、下一步检查入口。

通信方式              当前生效：轮询  |  期望：轮询       [修改]
事件处理              待处理 N / 失败 N / 过期租约 N   [查看处理记录]

高级诊断（默认收起）：能力探测、设施、Worker、队列、原始原因码
```

`status=ready` 显示“正常”；实时模式的 `status=degraded` 显示“主动更新暂停”，保留 `effective_mode=realtime`，提示管理员修复依赖或手动切换轮询。不要把 `ready=null` 或“该模式不需要的能力”计为故障；轮询模式下未启动 Gateway/Worker 要按后端能力语义标为“不需要”，不能仅用设施 `ready=false` 汇总红色告警。事件队列的失败数须明确为全部队列还是通知队列，未补专用汇总前标“事件处理”，不标“通知失败”。

### 修改通信方式

由“修改”进入同页配置区或原生对话框，分两组：

1. **通信方式**：轮询 / 实时。选实时前显示 Redis、Gateway、Worker 依赖的真实探测结果；任一必需依赖不可用时服务端拒绝开启，不能把失败写成“已经切换成功”。
2. **刷新频率**：普通设置显示通知、私信、未读数三个间隔及“页面隐藏时暂停”。退避倍率、最大间隔、三个心跳过期窗口和 Supervisor 要求放在“高级参数”，标注适用模式与单位。不要把 `require_supervisor` 表述为能够在后台启动 Supervisor；现有实现只是部署要求/探测策略。

仅有 `operations.runtime.configure` 的人看到修改入口。表单与快照比较，没有修改则禁用应用；打开确认框前调用现有 validate，失败时停留表单显示校验错误。确认框逐项列出模式、轮询间隔及高级参数的实际前后值，并说明“实时故障时保持实时模式，需修复依赖或手动切换”；409 读取最新快照但保留未保存草稿，关闭旧确认框并提示重新审阅。重新探测只更新诊断，不与“应用配置”放在同一主操作层。

### 状态与跳转

- 加载失败时保留上次成功快照并标“数据可能过期”，展示上次检查时间；不能把过期数据称为当前正常。
- 无 Worker 记录时区分“当前模式无需常驻处理器”和“该模式要求但未启动”，由模式与探测结果判断。
- “查看处理记录”进入通知投递页并预选异常筛选；“查看策略”进入通知策略页。

## 二、通知投递：先找需要处理的记录

页面标题建议改为**通知处理**，副标题写“检查站内通知对应事件的处理记录；成功处理不表示用户已阅读”。导航与路由可保持原路径，避免链接迁移。

```text
通知处理                                      [刷新]
待处理 N   处理中 N   失败 N   已按策略跳过 N    统计时间范围/最近更新

[需处理] [全部]    状态筛选    事件类型筛选（可选）
记录：业务事件/处理结果 | 当前状态 | 尝试次数 | 可执行/更新时间 | 操作
失败行：失败摘要 + [查看详情]；人工重试放在详情页
```

默认“需处理”应是 `dead` 与超过可接受等待时长的 `pending` / 过期 `processing`；普通短暂 `pending` 不应一律标故障。具体等待阈值需由后端明确提供或使用已有运行时配置，前端不得用本地时间猜测。若首期只实现单状态筛选，默认落在“失败”，并提供“全部”；不伪造“需处理”计数。汇总和列表要使用相同的通知队列口径，显示统计更新时间。状态过滤、分页与 URL query 同步；浏览器后退须恢复筛选和页码，请求失败时不得把旧筛选记录显示在新筛选下。空态按筛选说明“没有失败记录”或“暂无处理记录”。

详情顶部显示可读的业务事件名、当前处理结果和下一步动作；其次显示错误、尝试次数及时间字段；事件 ID、处理器键、关联 ID、执行模式和策略版本收进“技术信息”。仅 `dead` 且有 `operations.retry` 时展示“重试”，确认文案明确“再次运行该处理器，可能对外产生通知”，成功后重新读取记录。策略关闭造成的 `completed + skipped` 不提供重试。

列表与详情都必须呈现策略判断字段。若后端只记 `applied/skipped/not-configured`，将 `applied` 写成“已执行通知投影”，不要推出浏览器已接收或用户已读。不要暴露 payload 或收件人私信内容。

## 三、通知策略：先说明开关会影响什么

页面标题保留“通知策略”，副标题改为“决定哪些业务事件生成站内通知；不会阻止业务动作本身”。列表以中文业务行为和影响对象为主，技术事件名仅在“技术信息”中展示。

| 分组 | 页面名称 | 关闭后的实际影响 |
| --- | --- | --- |
| 互动提醒 | 新关注提醒 | 关注关系照常建立；不生成该关注站内提醒 |
| 互动提醒 | 私信提醒 | 私信照常送达并可刷新列表；不生成站内提醒记录 |
| 互动提醒 | 点赞提醒 | 点赞照常生效；不生成相应点赞提醒 |
| 互动提醒 | 收藏提醒 | 收藏照常生效；不生成相应收藏提醒 |
| 互动提醒 | 评论与回复提醒 | 评论照常发表；不生成对应评论/回复提醒 |
| 互动提醒 | @提及提醒 | 提及照常保留在内容中；不生成对应站内提醒 |
| 必须发送 | 系统安全与审核通知 | 受保护；不可关闭 |

“点赞”和“评论”各有多个最终通知类型，不能按单一 `notification_type` 标签误导；管理 API Resource 中的业务名称和影响说明要与后端事件目录同步，并用契约测试锁定。`recipient_rule=handler` 不作为管理员信息展示。每行显示“已开启/已关闭”、影响一句话和开关；受保护行以“始终开启”说明原因，不显示看似可以点的灰色开关。版本号与 CAS 原理放在技术信息或确认弹窗，不占页首。

更改后出现固定底部保存栏：`已修改 N 项`、`放弃修改`、`审阅并保存`。审阅弹窗逐项列出“从开启到关闭/从关闭到开启”和影响，说明**仅影响新登记事件**，在途事件仍按登记时的版本处理；操作者、版本和原因写审计。原因字段按现有 API 可选，不要在首屏作为独立大表单。409 冲突时不静默覆盖草稿，应提示重新载入后的变化并让管理员再次确认。离开页面时提示未保存修改。无 `communications.configure` 权限但有 `communications.read` 时，仍可只读展示策略目录；GET 使用 `communications.read`，PUT 使用 `communications.configure`。两项能力保持正交，配置角色必须同时授予 `communications.read` 才能进入并读取目录，不能假设 configure 自动蕴含 read。页面不能用操作权限包裹整个目录，开关和保存栏按操作权限隐藏。只读权限必须有浏览器回归，确保能看到真实开关状态但不能提交修改。

## 文案与技术字段规则

| 当前写法 | 管理员写法 | 保留位置 |
| --- | --- | --- |
| desired / effective | 已选择 / 当前生效 | 运行状态首屏 |
| Gateway、Worker、Scheduler | 实时连接服务、事件处理进程、定时任务 | 异常原因；原名在高级诊断 |
| Outbox、handler、request_safe | 事件待处理、处理器、请求内处理 | 投递详情技术信息 |
| CAS、policy_revision | 配置版本冲突、策略版本 | 确认/冲突提示与技术信息 |
| completed + skipped | 已按策略跳过通知 | 处理列表和详情 |

文案必须依据后端真实字段；不承诺“已到达浏览器”“用户已收到”“自动恢复”或“Supervisor 已启动”。正常态不堆叠成功提示；异常优先给出原因、影响和下一步。

## 施工拆分与验收

1. **主开发：先修正确性。** 核对 dev 当前策略版本与事件目录；添加向前的修复迁移/版本生成，保证三个事件名对齐且历史冻结版本不变；补 `policy_decision`/`policy_revision` 只读字段、通知队列筛选与同口径汇总；更新 SDK 生成产物。验证六类互动开关的开/关、旧在途投递、重试、受保护系统通知和并发版本冲突。
2. **管理端：三页垂直改造。** 在现有页面、共享组件和导航中实现上述信息层级与状态；不新建第二套 API 客户端或仪表盘。先运行状态，再投递列表/详情，最后策略；每一步使用真实 SDK 字段。列表筛选、只读权限、未保存草稿、异常和空态都做浏览器验收。
3. **复审：核对语义与跨页链路。** 实测“关闭一种提醒 → 业务动作仍成功 → 新事件显示按策略跳过 → 浏览器无该提醒”；再开启后只影响新事件。实时不可用时应保留实时模式并提示主动更新暂停，管理员手动切到轮询后恢复定时读取；不借 UI 验收重启共享 dev 服务。

每个代码切片按根 `AGENTS.md` 执行 `npm run check`；管理端改动再执行 `npm run build:admin` 和对应 E2E。设计稿本身只需检查文档链接、代码指向与 diff。

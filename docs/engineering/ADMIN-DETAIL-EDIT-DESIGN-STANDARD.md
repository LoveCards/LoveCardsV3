## 1. 设计目标与行为边界

管理员进入对象时，第一屏应回答“这是谁／是什么、当前状态、主要内容、下一步可做什么”。对象所属主列表的编辑、处理及必要的只读诊断在弹窗完成；其他模块或记录中的引用、站内跳转、书签和直接访问进入该对象的独立详情页。独立页是这条记录的稳定管理地址，具备权限时可在同一详情主体中编辑或处理。两种容器共用模块内的读取、权限、草稿、验证、保存与刷新规则。不得把 Nuxt page 嵌入弹窗，也不建立全局 schema 表单引擎。

查看态是默认阅读状态。具备权限时，编辑入口只让该保存范围的可写字段在原位置切换为控件；时间、ID、操作者、关联事实和审计记录继续只读。审核、封禁、隐藏、恢复、置顶、重试、删除等是资源命令，按真实单条契约和对象状态呈现，不伪装成字段编辑。普通编辑与有副作用的专题操作分开提交和确认。具备权限且状态允许的独立命令在字段编辑态仍应可触达；未保存的字段草稿不能成为静默禁用命令的理由。命令确认须说明草稿仍需单独保存，执行后刷新命令状态而不覆盖草稿或关闭正在编辑的弹窗。正在保存、上传或执行命令时才临时禁用冲突操作。

### 1.1 入口按来源确定，不按操作能力拆页面

| 来源 | 目标 | 首次状态 |
| --- | --- | --- |
| 对象所属主列表的“编辑”及单条处理命令 | 保留该列表上下文的详情弹窗 | 直接进入对应编辑或处理范围；无权时不提供动作 |
| 对象所属主列表的必要只读“查看” | 保留该列表上下文的详情弹窗 | 阅读态 |
| 其他资源、审计、任务、通知等位置对该对象的引用 | 该对象稳定的独立详情页 | 阅读态；可在页内进入获授权的编辑或处理范围 |
| 书签、地址栏、刷新或新标签页 | 同一独立详情页 | 阅读态，不依赖来源列表状态 |

对象所属列表的身份字段不承担详情导航，也不为了暴露独立页而增加“查看”按钮。弹窗不承担独立页的发现任务；“打开完整页面”不是弹窗必备底栏或第二个主操作。若确有复制地址或跨任务继续的真实需求，可提供次级入口，但须说明其任务，并按未保存规则离开。引用链接始终说明目标对象，不把普通字段或当前行 ID 伪装成按钮。

### 1.2 独立页维护一条对象记录

独立页的中心是由 SDK 单条读取契约标识的**一条资源记录**：可读身份、业务字段、当前状态、受权可写字段及该记录的真实命令。展示顺序按管理员识别和决策需要组织，不逐列照抄数据库表，也不暴露未授权字段或原始存储结构。关联对象、引用、处理历史和审计是解释这条记录的辅助信息；有独立权限或流程的专题仍使用自己的区块或子页，不把多个对象的管理任务混成一个总览看板。

独立页与列表弹窗使用同一模块详情主体；两者的身份、字段顺序、编辑范围、命令、校验、错误和保存结果一致。页面外壳只增加面包屑、返回与稳定 URL，弹窗外壳只负责标题、关闭、焦点和滚动。可用宽度可以改变列数、滚动和操作区位置，不改变对象事实与授权能力。只读资源和只读权限不制造编辑控件；“维护”仅通过已有 SDK/API 契约执行，服务端仍作最终裁决。

## 2. 可审查的视觉基线

### 2.1 两种容器，一份主体

```text
独立页：AdminPageContainer（资源详情 1040px）
  AdminPageHeader：面包屑 / 唯一 h1 / 返回
  同一详情主体：记录身份与状态 → 核心字段或证据 → 关联 → 历史与诊断
  授权编辑：在主体的对应范围原位切换字段并提交

主列表弹窗：v-dialog → v-card（唯一浮层表面）
  紧凑标题行：同一对象身份 / 状态 / 关闭
  同一详情主体：与独立页相同的事实、区块、字段和命令，不再套第二层 v-card
  编辑入口：直接进入对应编辑范围；取消 / 保存由该范围提供
```

独立页的 `AdminPageHeader` 是页面唯一大标题；主体身份行不重复同级标题。弹窗标题和关闭属于壳，业务字段和操作属于主体。弹窗中的关联资源链接可导航到对方独立页，离开前遵守未保存保护。弹窗不改当前列表查询 URL。

### 2.2 表面、分区和留白

- **只保留一层主表面。** 独立页用一张 `flat + border` 的 Vuetify 表面，弹窗用自身的 `v-card`；主体内的普通区块不再额外加卡片边框、阴影或大圆角。媒体缩略图、代码块、证据快照等有明确自身边界的数据可局部描边。
- 主表面内边距桌面 24px，窄屏 16px；身份区与首个内容区间隔 24px；相邻普通区块间隔 24px，用一条细 `v-divider` 或留白分组，不能每段都叠加边框。短字段行距 16px；同一组标题与内容间隔 12–16px。
- 区块标题使用现有 18px/600 层级，说明为次级正文；普通标签为 14px、中性次级色，值为 16px 正文色。一个区块最多一个强调焦点：主要内容、证据或当前状态。不要给每个字段配前置图标、粗体标签、彩色背景或独立按钮。
- 首屏身份行显示资源真实名称、状态和必要上下文；没有标题字段的内容资源只显示“资源类型 #ID”，不得截取正文伪造标题。对象编号在主体身份区出现一次即可，不在元数据字段中重复。IP、correlation ID、原始 payload 等放后部诊断区，可按需展开。
- 状态使用文字与语义色，只有异常或待处理状态需要明显 `v-chip`；正常值优先普通文字。沿用现有主题 token，浅色与暗色保持相同信息层级，不逐页写固定白底或深色覆盖。

### 2.3 字段与内容

- 只读短字段统一为“标签在上、值在下”的平面字段。桌面通常两列，窄屏一列；不要用 3–4 列把中文值挤窄。长正文、审核证据、错误栈、媒体及可编辑富内容独占整行。
- 值可复制或可跳转时，交互只附着在该值或紧邻的明确文字入口。关联对象显示“名称 #ID”，缺名称时显示“资源类型 #ID”；链接必须有稳定目标路由和可识别的文本样式。普通 ID、编号和只读事实不是按钮。
- 长文本先给可读正文或适度摘要，全文与上下文同处详情；使用换行和最小宽度约束，不横向撑破弹窗。原始 JSON、请求参数和错误堆栈采用等宽、可换行或局部滚动的诊断容器，不染色整页。
- 空值用统一的“—”；加载、失败、无权和内容为空分别表达。刷新中的旧值不得伪装成最新值。

### 2.4 查看、编辑和保存

- `查看`入口进入阅读态；`编辑`使当前可写范围在原位变成 `outlined`、`comfortable` 的 Vuetify 控件。标签、字段顺序和组标题保持不动，避免切换时页面重排。只读事实仍用平面字段，不用禁用输入框占位。
- 一个保存范围同一时刻只有一个主提交按钮，文案按结果写“保存修改”“保存授权”“提交处理”等；取消紧邻保存。独立页与弹窗共享同一动作，不在弹窗壳再加一组“保存”。保存中禁用重复提交，错误靠近该范围，成功后重读服务端事实。
- 多个独立范围不可合成一个虚假的全局保存：用户资料、角色授权、账号安全、卡片媒体上传、举报状态与备注分别处理。单次只打开一个编辑范围；切换范围或离开前处理脏草稿。上传已经发生的副作用需要就近说明，不能暗示取消会回滚。
- 资源命令放在主体后部清晰命名的操作区，或在高频任务下放在身份区附近；危险与不可逆命令在确认层写明对象、影响和后果，确认前不整页标红。无权限或无有效命令时不显示空操作区。
- 常驻 `v-alert` 只用于会影响当前决策或阻断操作的事实；普通组件说明放在字段帮助文本，保存错误放本范围，成功使用短反馈。不能用连续提示卡代替信息层级。

### 2.5 弹窗尺寸、滚动与可访问性

弹窗宽度按内容复杂度选三档：简单对象约 720px，正文或多范围编辑约 880px，证据／审计／诊断约 1040px；同类资源固定一档，不逐页随意取 760、840、900 等尺寸。这里的数值是本仓库的设计决策，非 Vuetify 官方规定。桌面最大高度不超过视口约 90%，标题与关闭保持可见，主体滚动；只有需要独立确认的当前范围可在底部显示单组动作。窄屏（约 600px 以下）统一全屏，内容单列，关闭和当前操作可触达，不出现页面级横向滚动。200% 缩放按窄屏检查。

打开时焦点进入标题或首个有意义控件，关闭后回到触发行；Esc、遮罩、切换对象、路由离开都受相同脏状态决策约束。确认对话框只有在明确命令时出现，不能与详情弹窗形成两个同时可操作的主层。标题层级、字段 label、错误关联和键盘顺序须可读。

### 2.6 内容型资源的视图样板

```text
独立页：卡片详情 → 卡片 #123                         [编辑]
弹窗：编辑卡片 · #123                                [关闭]
两种容器的主体都是同一张连续表单，按重要性排布：
正文（完整多行）
图片（多图预览、顺序、封面、移除与添加）
标签（已选 chip 与搜索候选）       发布范围
扩展数据 JSON（完整多行）
审核与发布状态                    置顶状态
作者                    发布时间                    互动统计
编辑态末尾：[取消编辑] [保存修改]
```

以上只是卡片的数据优先级样板，不要求其他资源按卡片字段建表。正文与 JSON 在阅读态完整展示，在编辑态原位使用 `v-textarea`；JSON 顶层须为对象，保存前就近校验。标签使用可搜索的多选 `v-autocomplete` 与 chip，不维护平行的自制选择器。图片选择使用 `v-file-input multiple`，预览用 `v-img`，编辑态在缩略图网格通过拖动手柄调整媒体顺序；手柄聚焦后可用方向键完成同一操作。排序后第一张图片自动成为封面，视频不参与封面选择；缩略图仅保留封面标记、拖动手柄和移除动作，不再提供上移、下移或单独设封面按钮。排序动画须遵循 Reduced Motion。图片上传的即时副作用、已上传但未绑定文件和旧媒体缺少文件 ID 的限制须如实说明。发布范围只有在管理 API 明确允许并经权限校验后才作为可写字段显示。审核、隐藏、封禁和置顶虽可用选择控件表达当前值与目标动作，但每次转换仍是独立的受权命令，确认后立即生效，不纳入普通草稿的“保存修改”。独立页在主体上方加面包屑与页面标题，弹窗使用紧凑标题行且不在主体重复编号。

### 2.7 按资源语义选择内容编排

共同的容器、字段和动作规则不等于所有资源采用同一张字段表。详情主体只选一种主要阅读顺序：

| 编排 | 适用对象 | 首屏焦点 | 后续信息 |
| --- | --- | --- | --- |
| 身份型 | 用户、角色、标签 | 名称、身份、当前状态 | 可写资料、授权或治理，再到技术标识 |
| 内容型 | 卡片、评论、举报 | 正文、媒体或证据及状态 | 作者与关联、治理、时间和诊断 |
| 诊断型 | 文件、审计、处理任务、权限目录 | 结果、异常或能力说明 | 关联事实、时间和原始技术信息 |

每个资源只保留一层主要阅读表面。无媒体时不渲染空的媒体区；诊断数据和有自身边界的预览可局部描边。普通分区由 AdminDetailSection 提供一致的 24px／16px 内边距与单条分隔线；弹窗的 v-card-text 使用 pa-0，防止壳与主体重复留白。独立页的查看态在所编辑内容附近提供授权编辑入口；主列表弹窗可直接进入同一编辑范围。取消与提交只由当前范围提供，弹窗壳不复制业务操作，也不把“打开完整页面”设为常驻导航底栏。

用户资料、账号状态、角色授权是三个互斥编辑范围；后两者不能依附于“编辑资料”模式。账号状态仍以服务端命令完成，遵循既有权限、通知和审计规则。资源命令如审核、隐藏、封禁、恢复及重试独立于普通字段保存。

### 2.8 用户与评论的施工前设计裁决（2026-11-22）

本节记录从 `UserDetailContent`、`CommentDetailContent`、`CardDetailContent`、两组路由／Dialog、SDK 类型及管理端写入契约逐项核对后的设计。**当前用户和评论实现尚未达到本节基线**；本节先冻结字段、动作与状态，不将代码存在或构建通过等同于视觉验收。施工只触及用户、评论详情主体及其容器；不改列表、SDK、通知或后端状态机。

共同规则：两者沿用卡片的**一张连续记录表单**，按字段重要性排布；只有页面外壳、弹窗标题和滚动方式不同。主体内不使用“账号概况／角色归属／评论治理”等三张并列任务板，也不以连续 `v-alert` 充当分区。一个字段在阅读态显示值，在授权编辑态原位置显示 Vuetify 控件；始终只读的字段保持平面值，不渲染禁用输入框。状态选择器显示**当前状态**，选择目标后才进入独立确认和写入；取消确认恢复当前值。状态、授权与普通资料的保存范围不得混合。正文、头像与账号身份优先，技术标识和统计后置，必要处只用细分隔线。正常状态用中性文字，异常状态才强化语义色。

| 资源 | 同一主体中的视觉顺序 | 原位编辑与只读 | 提交边界 |
| --- | --- | --- | --- |
| 用户 | 头像与用户名 → 账号号码 → 邮箱、手机号 → 账号状态、角色 → UID 等确由单条契约返回的辅助事实 | 头像预览与上传、用户名、邮箱、手机号属于资料草稿；账号号码和 UID 锁定为平面值。邮箱／手机阅读态沿用受控遮罩，编辑态使用原生字段。角色以“名称 #ID”chip 呈现，授权后原位换成可搜索的多选控件 | 资料一组保存；角色授权一组保存；状态下拉为即时命令。资料与角色草稿互斥，切换前先处理未保存内容；状态命令在资料编辑中仍可用。头像选择后立即上传，预览用新 URL，提示取消不会撤销已上传文件 |
| 评论 | 完整正文 → 作者、所属卡片、父评论 → 审核状态、置顶状态 → 点赞与时间等辅助事实 | 正文阅读态完整换行，编辑态同位置 `v-textarea`；关联值才是可导航链接。状态与置顶在有权且状态允许时为当前值下拉，其他情况为平面值。回复不可置顶，已删除评论无虚假编辑控件 | 正文单独保存；审核、隐藏、封禁、恢复与置顶只使用现有 `commentGovernanceActions`／SDK 命令，经确认立即生效。命令完成只刷新事实且保留正文草稿 |

用户独立页页头以“用户 · 用户名”识别对象，主体内保留一次“用户 #ID／账号号码”；弹窗壳以同一用户身份命名，不使用泛化的“编辑资料”替代对象身份。评论独立页和弹窗壳使用“评论 #ID”；正文不伪造标题，主体不再重复编号。两者在 1040px 独立页与 880px 弹窗使用同一字段顺序；桌面短字段最多两列，长正文、上传与角色选择独占整行；600px 以下弹窗全屏且字段单列。编辑入口在独立页的主体动作区，主列表编辑弹窗直接进入编辑态；底部只有**当前普通保存范围**的一组取消／保存，命令确认使用独立的危险动作 Dialog。主体不能同时出现页面保存栏和弹窗保存栏。

**契约边界：** 当前管理端用户 PATCH 只接收 `avatar`、`email`、`phone`、`username`、`status`，角色使用 `assignRoles`；`number` 不得因表单视觉被误设为可写。用户类型中的 `bio`、`location`、`gender`、`birth_date` 若单条响应确有值，可在辅助事实中只读展示；没有管理端写入契约前不得增加编辑输入。当前管理端 `CommentResource` 不返回旧 `data`、`post_ip`；不得根据 SDK 的可选类型或列表旧字段伪造“扩展 JSON／发布 IP”详情。若未来单条契约增加字段，先更新本表，再决定只读或可写。评论正文继续遵守服务端 140 字与非空约束，写入与状态命令不得合并成一次 PATCH。

**需要修正的现状：** 用户当前三个 `AdminDetailSection` 形成三层相似任务表面，状态同时有“当前状态”和“调整账号状态”两个视觉字段，头像上传与当前头像分离，角色的 chip 与多选控件重复；评论当前状态 chip、正文、关联分隔、治理按钮彼此断开，阅读态与编辑态的正文标签不一致，旧扩展字段可能与单条契约不符。评论保存成功后若重读失败，`load()` 会令整块 `AdminAsyncState` 显示错误并遮掉草稿；需保留编辑正文和就近错误，同时让主列表知道写入已发生。用户弹窗标题不包含目标身份，也需与独立页统一。

**施工顺序与可执行验收：** 先用 Mock API 固定用户资料／角色／状态、评论正文／治理的现有请求边界与脏状态，再逐一迁移用户、评论的独立页和列表弹窗。两者都检查：相同字段与顺序、一次编号、阅读／编辑切换不跳位、只读权限、命令期间保留草稿、写成功而重读失败不吞草稿、Esc／遮罩／关联链接的离开保护、保存后列表刷新和回焦。浏览器视口 1440／960／600／390px、浅色／暗色、200% 缩放与 Reduced Motion 截图需人工确认主表面、留白、可读性及动作可达；自动测试只证明交互，不代替审美签收。

## 3. 资源内容顺序与保存范围

| 资源 | 首屏与区块顺序 | 编辑／处理范围 | 后部信息 |
| --- | --- | --- | --- |
| 用户 | 账号身份、状态 → 资料与角色 | 资料、头像、角色授权、账号安全各自独立；封禁／冻结为命令 | 注册与登录事实、审计 |
| 卡片 | 状态 → 正文与媒体 → 作者和标签 | 正文／标签、媒体副作用；审核、隐藏、置顶、封禁等为命令 | 计数、时间、诊断 |
| 评论 | 状态 → 全文 → 所属卡片与作者 | 正文；审核、隐藏、置顶等按真实状态为命令 | 时间与审核记录 |
| 标签 | 名称、状态 → 描述和关联 | 基础字段；停用／恢复为命令 | 引用和时间 |
| 角色 | 名称、状态 → 能力摘要 | 基础字段、授权分别保存；删除受保护规则约束 | 成员与审计 |
| 文件 | 文件预览、状态 → 元数据与引用 | 元数据、公开／审核状态按现有契约分别处理；删除／恢复为命令 | 存储与诊断 |
| 举报 | 当前状态 → 举报理由、目标证据 → 举报人 | 状态处理和追加备注分开提交 | 处理历史与时间 |
| 权限目录 | 权限名称与说明 → 归属 | 只读，无编辑入口 | 技术标识 |
| 审计日志 | 动作、对象、操作者 → 变更摘要 | 只读，保留查看诊断入口 | 请求链路与原始记录 |
| 处理任务 | 状态、对象 → 结果或错误 | 重试是受条件约束的命令；其余只读 | 时间、重试记录和诊断 |

上述顺序是视觉与阅读优先级；字段是否存在、是否可写以及命令是否显示，仍由当前 SDK 契约、capability、目标状态和服务端规则决定。只读详情入口仅在审计、处理任务、权限目录等确有完整诊断阅读价值时保留。

## 4. 组件组合与迁移边界

优先组合 `v-dialog`、`v-card`、`v-card-title`、`v-card-text`、`v-row`／`v-col`、`v-divider`、`v-form`、`v-text-field`／`v-textarea` 等现有 Vuetify 组件。`AdminDetailSection` 可承载标题和内容插槽，但应支持**无额外表面**的详情主体布局；不能为了这份规范再造字段 schema、通用保存状态机或全局详情服务。模块内的 `*DetailContent` 继续负责业务读取和模式，路由页与 Dialog 只负责各自容器。

已迁移页面应遵守单一主表面与互斥编辑范围；历史页面中的逐段描边卡、图标字段或弹窗第二层卡片仍属于待迁移项，不得反推为新页面样板。一次迁移一个资源垂直切片，同时核对独立页、列表弹窗、权限、保存、确认与关联链接；验收后移除该资源旧样式和重复流程，不长期双轨。先用卡片与用户验证内容型和多保存范围两种情况，再迁移评论、举报、标签、角色、文件，最后收束权限、审计、处理任务的只读诊断。

## 5. 人工视觉验收

每个资源在浅色与暗色、1440／960／600／390px、等效 200% 缩放下，至少检查：

1. 独立页从非主列表引用或直达时能立即识别同一条记录、状态和主要内容，并可按权限编辑；主列表编辑弹窗直接进入同一编辑范围。两种容器字段顺序一致，不重复大标题或保存区。
2. 普通区块只有一层主表面；边框、图标、提示、色块和高亮不会抢过正文或证据。
3. 标签和值的层级一致；长内容可读；关联链接与普通值、按钮的语义清楚；技术标识不占首屏。
4. 查看切编辑时字段位置稳定；只读事实不变成禁用表单；每个保存范围只有一个提交区，取消及失败状态可理解。
5. 命令只在有真实契约、权限与状态时出现；危险确认说明影响；只读资源保留必要诊断入口。
6. 弹窗滚动、关闭、焦点回归、脏状态保护和窄屏全屏可用；没有横向溢出或被遮挡的动作。
7. 逐个核对主列表编辑、跨资源引用、直接访问和刷新四条路径；独立页维护目标记录而非列表摘要，关联与诊断不抢占主要字段。

自动检查至少运行 `npm run check`；修改管理端运行码再运行 `npm run build:admin` 和相关 E2E。构建通过不能代替上述截图人工审查。

卡片垂直切片的已执行检查与待人工确认项见[卡片详情验收基线](ADMIN-CARD-DETAIL-ACCEPTANCE-BASELINE.md)。

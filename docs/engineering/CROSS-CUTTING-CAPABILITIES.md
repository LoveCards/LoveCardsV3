# 跨业务能力接入与集中管理规范

> 本文规定新增与收束跨业务能力时的边界；各切片的最终验收以代码与 CI 为准。
>
> 适用范围：验证、防滥用、审计与通知义务、外部服务依赖，以及已有的事件、权限、配置和运行时目录。

## 1. 要解决的问题

同一种能力可能由多个业务使用。管理员需要回答三个问题：**哪里使用、按什么规则执行、当前是否有效**。目前这些答案有的在路由，有的在业务代码、配置、驱动或运行时状态中。仅有一个配置开关或一张驱动列表，不能证明业务入口已经接入，也不能证明整条依赖链可用。

本规范统一的是**接入关系的表达、检查和管理端呈现**，不统一各领域的业务执行。优先消除重复事实源和失效后显示“正常”的情况。

## 2. 不变量与熵预算

1. **一个事实只有一个所有者。** 权限以 Route access、RBAC capability 为准；事件处理以 Handler Registry 为准；通知与信号开关以各自版本化策略为准；系统配置以 Config 为准；业务状态以所属模块为准。集中视图只引用它们，不复制成第二份可编辑策略。
2. **目录不代替执行。** 登记某个接入点不能自动宣称它受到保护；必须能追溯到实际路由或用例，并有行为测试验证。管理端隐藏按钮不等于后端授权。
3. **不建万能总线。** 即时验证、权限和限流仍同步执行；已发生的业务事实才进入 Eventing；审计与用户通知遵守各自事务和投递规则。不得为“统一”增加第二套事件、配置、任务或审计账本。
4. **先引用，后抽象。** 现有目录足以回答问题时直接复用；只有出现已确认的重复或漂移，且现有机制无法检查时，才增加领域内的场景声明。只为页面排版增加的后端注册层不予接受。
5. **读写分离。** 集中视图可以跨域只读聚合；修改仍调用各领域现有 API、权限、版本校验与审计。页面不得把多个独立提交展示成一次原子保存。
6. **状态须附证据。** “已声明、已配置、策略已开启、依赖就绪、实际健康”是不同事实；不能折叠为单个 `enabled`。未知或探测失败显示未知/故障及原因，不回退为健康默认值。

新增持久表、通用执行器、通用策略编辑 API、第二份可写目录、跨域全局开关，均不属于本设计。确有新需求时须以具体耦合和迁移成本单独论证。

## 3. 统一的接入关系

管理端需要的最小只读关系是：

```text
业务入口（HTTP 路由或领域用例）
  → 所属模块
  → 所需能力与执行位置
  → 策略/配置的权威来源
  → 外部依赖
  → 当前状态及证据
  → 对应的管理入口
```

HTTP 层引用已有 `route name`，领域层引用自身已有的场景、审计动作或事件标识；**不得为了统一视图发明全局操作 ID，也不得让 Domain/Application 依赖 HTTP 路由名**。没有现成标识且不影响执行的关系，只在展示或测试中定位来源，不强迫业务新增键。领域公开的目录只包含必要的名称、依赖关系和可展示状态；不得把密钥、完整用户数据、验证码或业务 payload 带入目录。中文名称与影响说明是展示信息，不参与 Handler Catalog 指纹或业务裁决。

| 问题 | 权威来源 | 集中视图能做什么 |
| --- | --- | --- |
| 谁能调用、请求字段是什么 | 路由 meta、Validate、RBAC 目录与 API 契约 | 引用 route name、权限和请求约束 |
| 是否需要即时保护 | 业务用例或路由的实际验证/限流接入 | 展示接入位置；检查声明与执行一致 |
| 是否产生后续效果 | 所属模块的事务、Eventing/Notifications/Audit 规范 | 展示事件、审计、通知义务及证据，不代替发布 |
| 策略当前值与修改权限 | Config 或领域策略状态 | 只读展示版本、状态及编辑入口 |
| 服务是否可用 | 驱动、连接测试、运行时探测 | 展示依赖原因与探测时间，不凭配置开关猜测 |

页面只展示各领域已有的状态事实，不定义跨域通用 `healthy` 布尔值。配置齐全只能说明“已配置”；本地依赖可用、外部连接测试成功、近期真实运行成功须分别标明证据来源和时间。缺少测试或权限时显示“未验证”或“不可查看”，不得合成“正常”。

第一阶段复用已有路由契约、领域目录、配置和行为测试，先在工程检查中核对关系，不为总览新建运行时接口。某个领域的管理页面确实需要缺失信息时，才由该领域通过 `Public/` 提供最小只读查询，再经现有 API 契约与 SDK 输出。跨域页面优先组合这些 SDK 查询；若多处页面重复相同联结且已形成真实耦合，再由 Operations/Administration **只经各模块 Public 入口**提供无持久状态的只读投影。业务模块不得反向依赖 Operations、管理端或其他模块内部类；投影不得成为新的执行或配置真源。

## 4. 各领域收束边界

| 领域 | 现状判断 | 目标设计与实施门槛 |
| --- | --- | --- |
| 验证 | 驱动可见；注册、卡片写入和修改邮箱的使用点分散；登录人机验证未接入 | 先用现有路由、调用点与配置建立可核对的使用关系；页面需要时由 Captcha 领域提供最小只读信息。先展示覆盖与依赖，再讨论场景级开关；目录不得改变当前验证要求 |
| 防滥用 | 登录、访客、接口防连点和上传限制分别执行 | 先在工程检查和文档中盘点保护入口、维度、阈值来源、窗口与存储依赖；有实际运维需求后才开放只读页面。环境配置与站点配置明确区分；未经独立授权设计，不开放后台修改安全阈值 |
| 审计与用户通知 | 有 AuditLogger、Eventing 和 Notifications 规则；动作义务分布在业务用例 | 复用《观测、日志与审计》《站内通知开发规范》的判定和现有动作/事件标识，在受影响用例中用行为测试验证事务成败、去重与收件人；不另建一份可漂移的运行时义务目录，也不建立自动替业务决定是否通知的通用 Hook |
| 外部服务 | Storage、Sender、Captcha 有各自的驱动发现和配置；业务用途与依赖链不完整 | 先在现有页面展示有证据的用途与依赖，缺少数据时才由所属领域补最小只读查询。驱动凭据仍在各自页面维护，不抽取跨域驱动基类 |
| 事件、权限、通知策略、主动信号、配置、运行时 | 已有专门目录、版本和状态所有者 | 直接引用现有目录和健康结果；不迁移到新的注册中心，不复制可写开关 |

内容审核、举报、账号安全和系统升级的状态转换仍由所属领域裁决。它们可以向集中视图提供接入与义务信息；不能为了共用页面而合并状态机。

## 5. 管理端入口规则

每类能力只保留**一个主要编辑入口**。跨域总览若实施，只承担搜索、依赖诊断和跳转，不提供第二组保存按钮。列表以管理员要完成的任务命名；技术键、执行位置和依赖链放在详情或技术信息中。页面按 capability 分区加载和显示，不能因具备总览读取权限而扩大任何领域的配置权限。

验证要求、服务设置和驱动配置在“验证中心”同一入口分区管理；“站点策略”只编辑访客浏览，并显示验证摘要和跳转。具体边界见 §8.1 与[《管理端菜单与页面归属规范》](ADMIN-NAVIGATION-CONVENTION-2026-11-07.md)。缺权限显示不可查看，不用默认值伪装已保存状态。修改邮箱等账号安全要求不得因统一 UI 变成可关闭的站点开关。

事件管理、审计日志、站外发送、文件存储等现有页面继续各自承担操作和调查。若以后建立“能力总览”，它是只读发现入口，不挤占上述页面，也不新增一级菜单；是否需要该页以跨域排障的实际使用需求决定。

## 6. 接入与变更检查

新增或修改跨业务能力时，按以下顺序判断并留下可执行证据：

1. 确认业务入口和所属模块；HTTP 入口复用 route name，领域内部沿用自身已有标识，不新增全局动作键。
2. 确认实际执行位置、策略所有者、依赖和失败语义；安全保护缺依赖时按领域规则失败，不以界面状态放行。
3. 涉及用户权益、账号安全、内容审核、互动提醒或站内公告的状态转换，先按《站内通知开发规范》判定通知；高风险动作按《观测、日志与审计》判定审计与事务边界。
4. 优先复用现有声明和契约；只有确有缺口时才补领域声明。对可机器核对的引用检查重复、未知和未接线；不能可靠静态判定的执行效果用行为测试证明，不用脆弱的源码字符串搜索冒充安全门禁。
5. 改路由或 API 时按现有生成链更新契约三件套与 SDK，并通过严格路由检查；管理端只经 SDK 读取，保持权限和错误状态可见。

## 7. 实施次序与验收

1. **基线盘点，无行为变更。** 从已有路由、目录、配置和测试形成接入矩阵；标明未知项，不推测已生效。优先核对验证、防滥用及高风险动作的审计/通知义务。
2. **验证单切片。** 复用现有键与配置，先用行为测试固定真实使用场景及依赖；只补页面确实需要的最小只读信息。保持现有开关语义、错误码和权限；新场景开关作为独立产品决策。
3. **防滥用与动作义务。** 各取一个真实场景验证现有契约和行为测试能否防止漂移；只有共同机制确实消除重复事实源时才推广，不预建全站规则引擎或义务注册表。
4. **外部依赖视图。** 在发送、存储等现有管理页面补有证据的用途和就绪信息；跨域只读总览须有实际排障需求才增加。

每个切片必须证明：目录与执行点一致；策略关闭、依赖缺失、探测失败和无权限时均不显示假健康；现有 API 行为不漂移；没有新增第二份可写状态；通过 `npm run check`，涉及管理端运行时再通过 `npm run build:admin`，真实 API 行为按《后端测试与质量门禁》在隔离环境验收。

每个实现 PR 还须列出熵预算：**新增权威状态源为 0、新增全局持久表为 0、新增跨模块内部类依赖为 0**。新增公共接口或声明时，指出它消除的重复事实或检查盲区；若存在旧路径，明确删除位置和时点。只增加一份需要人工同步的名单，不满足本规范。过渡双轨必须写明删除条件并在同一切片收束，不能把设计文档当作长期兼容层的理由。

本文件只规定跨域关系和准入边界。各领域的具体执行语义继续由[《模块架构与依赖规则》](MODULE-ARCHITECTURE.md)、[《事件总线》](EVENTING.md)、[《站内通知开发规范》](NOTIFICATIONS.md)、[《系统配置与共享基础设施》](CONFIGURATION.md)、[《观测、日志与审计》](OBSERVABILITY.md)及[当前管理端规范](ADMIN-NAVIGATION-CONVENTION-2026-11-07.md)维护，避免复制出另一套长期规则。

## 8. 具体实施方案

以下方案是本规范的第一版实施基线。它先解决已确认的分散接入，再决定是否有必要扩大抽象；没有列出的能力不预建通用平台。

### 8.1 验证：复用现有执行链，补最小使用视图

#### 后端

沿用现有 `Captcha` Public、`CaptchaCheck` 中间件和所属业务用例的同步校验。调用点和行为测试记录实际接入，管理端据此展示场景：

| 展示项 | 当前执行点 | 当前策略/依赖 |
| --- | --- | --- |
| 注册联系方式验证码 | `Session` 获取验证码、`RegisterUser` 注册；缓存场景 `Auth` | 注册方式及邮件、短信验证开关，分别依赖 SMTP、SMS 和验证码服务 |
| 注册人机验证 | `Session` 注册 | `captcha.captcha_enabled`、默认人机驱动 |
| 卡片创建/编辑人机验证 | `me/cards` POST/PATCH 的 `CaptchaCheck` | `captcha.captcha_enabled`、默认人机驱动 |
| 修改邮箱邮件码 | `Profile` 修改邮箱和获取验证码；缓存场景 `Info_BindEmailCaptcha` | 强制验证码、`captcha.code_enabled`、SMTP 发送渠道 |
| 登录人机验证 | 当前未接入 | 明确标记“未接入”，不显示为已保护或可开启 |

页面通过现有 SDK `config.list`、`captcha.drivers`、`captcha.config` 与 `session.policy` 读取配置、驱动和注册策略；Sender 管理接口仍按 `sender.read` 授权。Captcha 模块通过 Sender Public 读取本地配置就绪状态，实际投递由站外发送测试。修改邮箱的强制要求仍由 User 用例裁决。

测试分别固定注册、卡片写入、修改邮箱的真实行为，以及路由组中只有 POST/PATCH 要求人机验证；管理端 E2E 再检查场景文案与这些受测行为相符。不能靠搜索源码字符串证明已保护。将来若新增使用点导致同一场景规则在两个以上模块重复实现或出现实际漂移，再基于这些测试评估显式场景协议；不能为了目录形式先建协议。此切片不新增数据库表、API、配置键或第二个验证码账本。

#### 数据与管理端

本切片不新增 `captcha.usages` 接口：它只能把一份手写使用点名单从页面搬到后端，仍无法证明接线，反而增加契约和维护点。由现有配置和驱动接口提供动态事实，页面维护少量场景说明，并用上述行为测试和管理端 E2E 防止说明漂移。`系统 → 验证服务`页面调整为“验证中心”工作台：

1. 使用场景：按上表展示已接入场景和登录的接入状态，分别显示策略要求、本地条件及外部投递状态。验证码服务或对应发送渠道不可用时，受影响场景依然要求验证。页面文案明确“接入说明以当前版本为准”。
2. 服务配置：复用现有驱动列表和动态配置表单。
3. 站点要求：在同一工作台编辑注册方式、邮件和短信验证及人机验证。继续使用现有 `config.update` 和各组 `__revision`；一个保存动作同时提交 `user` 与 `captcha` 时，由 Config 现有多组事务整体提交。HTTP 409 保留编辑值并要求重新加载核对。验证码服务开关、站点要求和站外发送凭据各自保存。
4. 诊断：只显示配置、驱动就绪和当前可获取的发送渠道信息，不把“配置存在”写成“外部服务可达”。发送测试仍要求 `sender.test`，并明确它会产生真实外部发送；未持久记录测试结果时，刷新后状态回到“未经测试”。

`站点 → 站点策略 → 访问与验证`保留访客模式；验证开关改为只读摘要和“前往验证中心”链接。该 Tab 的访客模式只需原有 `config.read/update`，验证摘要单独按 `captcha.read` 显示；缺此权限时明确显示“无权查看验证设置”，不阻断访客模式，也不填默认值。这样只有一个验证编辑入口。实施前同步修订导航规范和对应 E2E；既有 `/apps/settings/verification` URL 保留，站点策略的 `?tab=access` 继续可用。

验证中心读取沿用现有 `admin.access + captcha.read` 与配置组级授权；配置写入继续需要 `config.update`，同时更新 `captcha` 组必须具备 `captcha.read`。显示 Sender 渠道信息仍需 `sender.read`，触发真实发送测试仍需 `sender.test`。不扩大权限，也不改变现有 API 契约。

### 8.2 防滥用：先统一可核对信息，不统一执行器

当前限制算法和维度不同：

| 保护 | 执行位置 | 维度/状态源 | 结论 |
| --- | --- | --- | --- |
| 登录与访客节流 | `LoginThrottle` | IP、账号、访客铸造次数；Cache/Redis | 保持 Auth 专属 |
| 注册、获取验证码和恢复防连点 | `SessionDebounce` | route name + IP，固定 6 秒；Cache | 保持认证 Host 专属 |
| 修改邮箱验证码重复发送 | `CodeDriver` 缓存场景与 `Profile` 错误映射 | 目标邮箱 + 场景，验证码有效期 300 秒；Cache | 保持 User/Captcha 现有链路 |
| 文件上传限流 | `CacheRateLimiter` | 用户 ID；Storage 配置 + Cache | 保持 Files/Storage 专属 |

它们没有共同的键策略、失败语义或管理员覆盖规则，因此不抽取全局 `RateLimitService`，不新增安全阈值管理页。第一阶段在 Auth、User、Files 的原有测试旁补矩阵：命中保护时返回既有错误与重试语义；不同账号、IP、场景或用户之间不串限额；缓存不可用时记录当前实际失败语义，若发现放行漏洞则作为独立安全修复切片处理，不借目录变更暗改线上策略。配置来源分别是 `auth_throttle`、`SessionDebounce` 常量、验证码缓存 TTL 和 Storage 渠道配置；页面只在相关配置旁说明受保护入口及来源，不提供跨域编辑。只有两个保护确实共享算法、存储和失败语义时，才单独论证合并。

### 8.3 审计与通知义务：复用现有规范和行为证据

不新增“义务注册中心”。

- 审计继续由所属用例调用现有 `AuditLogger`；事务归属、失败记录和字段脱敏按《观测、日志与审计》逐用例判断，不另造全局审计包装器。
- 用户通知继续遵循 `NOTIFICATIONS.md`，互动事实走 `DomainEventBus`，系统事实走 `SystemNoticeIssuer`，通知投递走现有 Handler Registry。
- 新增或修改状态转换时，在所属模块增加行为测试，验证真实状态变化、事务回滚、幂等、自通知排除和收件人；测试文件就是执行证据。
- 现有架构检查继续约束非法依赖和直接写 `notifications` 表；无法静态证明“应通知而未通知”或“应审计而未审计”，由状态转换测试与评审清单负责，不把源码字符串名单伪装成强保证。

第一批行为证据优先选两类已存在的高风险转换：用户邮箱变更核对 `security_version`、会话撤销、系统通知与审计同一成功事实，失败时均不新增；举报终态转换核对收件人、通知去重、审计及重复请求。测试复用各模块现有替身和隔离数据库门禁，不增加一份运行时“义务目录”。管理端事件页、通知策略页和审计页保持各自职责：事件页展示 Handler/投递事实，通知策略页修改策略，审计页调查动作；页面之间只提供链接。

### 8.4 Sender、Storage：只补用途视图，不抽跨域驱动基类

Storage、Sender、Captcha 继续各自使用 Factory、驱动 `meta()`、Config 和专用管理 API。它们已经共享足够的驱动形状，不再增加跨域父类或万能 `Integration` 接口。

后续需要“谁在使用”时，按所属领域补最小只读信息：

- Sender：已确认的业务调用是 Captcha `CodeDriver` 经 `Sender::code` 发送注册和修改邮箱验证码；管理测试会经同一 Public 能力发送测试码。现有模板目录是驱动能力，不能据此声称其他业务已接入；Notifications 当前使用站内投递，不列为 Sender 消费方。站外发送页可展示上述用途说明和当前渠道配置，凭据、默认渠道和测试动作仍在本页。
- Storage：已确认的上传场景来自 Files 的 `FileConstants` 和上传 Validate：卡片、评论、头像、资料封面、直传。页面可引用这些用途及 `UploadLimits` 的头像类/内容类划分；实际大小、格式还受渠道和厂商约束，不能只按一层配置推断最终可上传。
- 两页将“已配置”“本次连接测试结果”“近期业务成功”分栏展示；没有相应证据时写“未验证”或“不提供此指标”。现有 Sender 测试会真实发送验证码，不自动探测、不保存成持续健康；Storage 测试也只代表该次结果。测试动作保留原 capability 和副作用提示。不得仅凭本页刷新后的配置值重建上次测试成功状态。

这部分优先修改现有 Sender/Storage 页面文案与有证据的只读字段，不新建用途接口或跨域反向依赖索引。后续只有两个以上页面确实重复相同关联查询，才由数据所有者的 `Public/` 提供最小查询，经现有 API/SDK 页面组合；仍不新增持久状态。验收覆盖有/无读取权限、无渠道、缺配置、测试失败、测试后刷新和外部服务不可达，不能显示假健康。

### 8.5 已有集中能力：只补关系，不迁移真源

| 能力 | 现有真源与页面 | 本轮具体处理 | 验收重点 |
| --- | --- | --- | --- |
| 事件处理 | Eventing Handler Registry、事件事实和投递账本；事件管理页 | 用现有 Handler/队列目录回答“已注册什么”，事件明细回答“发生了什么、处理到哪”；其他页面只链接，不把同步验证和限流写入事件账本 | 新 Handler 显式装配、队列合法、事件事实与投递任务可追溯；无处理器的事件按 Eventing 现有语义显示 |
| 权限 | Route access、RBAC capability/scope、管理端导航契约 | 验证中心和站点摘要沿用原 capability，按组级授权分区；不创建“能力中心”再维护一份权限映射 | 无权限无法读组或写组，按钮隐藏不能代替后端 403；导航和面包屑与页面一致 |
| 配置 | Config 分组 schema、`__revision` 与组级授权 | 验证页把现有 `user`、`captcha` 配置放到一个任务入口；需要同时保存时使用一次多组提交，驱动组仍按自身范围保存 | 冲突全部不落库，返回本次脱敏快照；缺失/旧 revision 不静默覆盖 |
| 通知与主动信号 | Notifications 策略和收件记录、Runtime 通信策略 | 验证结果和限流结果只在请求内返回，除非发生《站内通知开发规范》规定的持久状态转换；不发“验证事件”来驱动页面刷新 | 只有真实状态转换产生相应通知；信号不承载业务数据，不替代收件记录 |
| 运行时 | Eventing 消费策略、Runtime 通信策略、Config Redis 连接 | 现有事件管理、前端通信和 Redis 页面各维护自己的配置；跨页只显示引用的就绪结果及跳转 | 策略选择、部署依赖和实测健康分开；诊断失败不显示自动切换或健康 |

上述能力若已有问题，按各自规范修正原页面或原模块，不开一条“跨业务能力平台”迁移线。跨域关系只有在真实排障场景反复需要时才评估只读总览；本次没有新一级菜单、持久目录或发布任务。

## 9. 契约、测试与发布顺序

具体实施按以下提交边界进行，每个切片可独立回退：

1. **验证行为基线切片**：在 `tests/Auth`、`tests/User`、`tests/Cards` 固定四类真实执行点、服务关闭/未就绪、无效挑战、修改邮箱强制验证，以及卡片 GET 不受写入中间件影响；不改运行时或 UI。
2. **验证管理切片**：调整验证页、站点策略访问面板和导航规范；只调用现有 SDK，沿用 Config 多组 CAS；补有/无 `captcha.read`、`config.read/update`、`sender.read/test` 的管理端 E2E，覆盖冲突、加载失败、刷新后测试状态、旧 URL/面包屑。若确需统一场景执行协议，再以测试证明的重复耦合单独设计。
3. **防滥用盘点切片**：补 Auth/User/Files 保护矩阵与相邻行为测试，记录缓存依赖和失败语义；不改变阈值、不开放后台总开关。
4. **外部依赖视图切片**：先修正 Sender 用途说明，再补 Storage 上传场景与证据分层；分别提交页面和测试，不共享写入接口。
5. **覆盖审计与通知切片**：按 §8.3 为状态转换补缺失行为证据；若发现真实漏发或漏审，按所属模块单独修复并遵循通知规范。

当前方案无新 API、表和生成物；若实现过程中确需改变路由或 API，必须重新导出契约三件套和 SDK，并运行严格路由、契约和生成物检查。每个切片至少运行 `npm run check`；管理端切片另跑 `npm run build:admin` 和相关 E2E，真实 API 行为在隔离环境运行 SDK 集成测试。每个 PR 的说明必须列出：新增公共接口（没有则写 0）、移除的旧调用、权限变化、行为测试、熵预算和未覆盖的外部连通性。

首批预计触及范围：验证测试在 `apps/backend/tests/Auth`、`User`、`Cards`；验证 UI 在 `apps/admin/pages/apps/settings/verification`、`apps/admin/components/site/SiteAccessPolicyPanel.vue` 和站点策略页；导航规则在 `ADMIN-NAVIGATION-CONVENTION-2026-11-07.md`；防滥用测试在 Auth、User、Files；发送与存储说明在各自现有管理页面。实际实施以每个切片的行为基线确认最小文件清单，不预先改动其他模块。管理端文案和权限变更要同步导航契约、面包屑及相关 E2E 断言。

## 10. 明确不做的事情

- 不建立跨业务万能 Registry、Event Bus、RateLimit Engine、Policy Engine 或 Integration Manager。
- 不把验证、权限、限流、通知和审计合并成一条运行时管道。
- 不让业务模块依赖管理端、Operations 聚合实现或 HTTP 路由名。
- 不新增跨域可写配置表、场景开关总表或运行时义务表。
- 不因为“统一入口”把独立 capability、CAS、审计事务和高风险确认合并成一次保存。
- 不把外部连接测试、一次人工执行或配置存在误报为持续健康。

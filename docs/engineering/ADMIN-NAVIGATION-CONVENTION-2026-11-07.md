# LoveCards 管理端菜单与页面归属规范

> 状态：生效
>
> 日期：2026-11-07
>
> 适用范围：`apps/admin` 管理端一级菜单、页面归属、页面标题、面包屑和入口迁移。

## 1. 目的

管理端菜单按管理员要完成的任务组织，不直接照搬后端模块、DDD 层级、驱动名称或部署拓扑。管理员首先需要知道“我要处理什么”，再进入页面查看技术细节。

技术架构仍然保留系统能力、站点策略和业务应用的边界；这些边界通过代码目录、权限、API 和页面内部的技术信息表达，不通过一级菜单强行暴露。

## 2. 固定一级结构

```text
工作台
内容
用户
站点
系统
```

一级菜单顺序固定为：

1. **工作台**：当前管理员的待办、健康摘要和最近变更。
2. **内容**：直接处理站点内容、治理和媒体资源。
3. **用户**：处理用户账号、账号安全和访问权限。
4. **站点**：决定站点对外展示、访问方式、内容规则和用户提醒策略。
5. **系统**：配置可复用基础服务，查看运行状态、投递、审计和升级。

菜单名称使用管理员熟悉的对象和任务。除“系统”外，不使用“能力层”“应用层”“领域层”“基础设施”等架构术语作为一级入口。

## 3. 当前页面归属

### 3.1 内容

```text
内容
├─ 卡片
├─ 评论
├─ 标签
├─ 举报处理
├─ 文件管理
└─ 社区洞察
```

“社区”只作为当前站点的一类业务描述，不作为一级菜单名称。举报和洞察虽然内部仍可使用 `community` 模块路径，菜单归入内容，因为管理员是在处理内容及其治理结果。

文件管理归入内容，原因是它管理站点中的媒体资源、使用关系和清理结果。存储驱动、对象存储凭据和上传基础设施仍归入系统。

### 3.2 用户

```text
用户
├─ 用户管理
├─ 角色管理
└─ 权限目录
```

“用户”负责谁在使用站点以及他们能做什么。角色和权限仍保持独立权限边界，不因为菜单合并而扩大数据范围。
用户端找回密码继续可用；管理端不再提供独立的恢复挑战列表。相关操作通过审计日志追溯，账号安全操作仍在用户详情中。

### 3.3 站点

```text
站点
├─ 站点信息
├─ 站点策略
└─ 主题外观
```

站点页面管理由系统能力组合出的产品策略：

- **站点信息**：站点名称、地址、介绍、页面标题、备案和版权。
- **站点策略**：以 Tab 组织访问与验证、内容规则、通知策略三个独立设置面板；每个 Tab 独立读取、保存并按自身 capability 控制。
- **主题外观**：站点使用的主题和外观配置。

“社区规则”统一改称“内容规则”。它描述当前页面实际管理的发布、审核和上传规则，不把 LoveCards 固定成唯一的社区产品形态。

### 3.4 系统

```text
系统
├─ 运行状态
├─ 通知处理
├─ 审计日志
├─ Redis 服务
├─ 存储服务
├─ 消息渠道
├─ 验证服务
└─ 升级与迁移
```

- **存储服务**：存储驱动、凭据、连接测试和渠道级限制。
- **Redis 服务**：可选的系统连接配置和连通性测试；默认关闭，实时模式启用前检查。
- **消息渠道**：SMTP、短信等发送渠道及其测试。
- **验证服务**：验证码驱动、验证码发送服务能力、默认驱动和驱动凭据。
- **运行状态**：事件消费策略（定时/常驻）与健康、前端通信模式（轮询/实时）与健康，以及 Worker、Gateway、定时运行记录和运行参数。
- **通知处理**：通知事件的投递、失败、重试和按策略跳过记录。
- **审计日志**：谁在何时改变了什么，以及请求和结果。
- **升级与迁移**：Release、数据库迁移和恢复流程。

## 4. 验证设置的归属

验证相关设置必须拆成两个页面，不能把系统服务开关和站点使用策略放在同一组“基础设置”里。

| 页面 | 设置 | 说明 |
|---|---|---|
| 系统 → 验证服务 | 验证码服务 | 邮箱/短信验证码能力是否可用 |
| 系统 → 验证服务 | 验证码发送渠道 | 通过 SMTP 还是 SMS 发送；凭据在消息渠道中维护 |
| 系统 → 验证服务 | 验证码默认驱动 | 选择实际的验证码服务实现 |
| 系统 → 验证服务 | 验证驱动配置 | SMTP code、图片验证码、极验等驱动参数 |
| 站点 → 访问与验证 | 注册邮件验证 | 注册时是否要求邮箱验证码 |
| 站点 → 访问与验证 | 人机验证策略 | 已接入的注册或写入流程是否要求人机验证 |

当前后端配置键可以继续使用 `captcha.code_enabled`、`captcha.code_channel`、`captcha.captcha_enabled` 和 `user.captcha`。菜单拆分不要求立即改配置键或权限名。

页面必须展示依赖关系：注册邮件验证或人机验证策略开启时，对应系统服务和驱动不可用，应显示未生效原因；不能把策略开关的开启状态直接当作验证已经生效。

当前人机验证只接入注册及 `me/cards` 的 POST/PATCH 请求；登录未接入。页面文案不得暗示登录已受此开关保护。

配置 API 对整个 `captcha` 组执行组级授权。站点策略的访问与验证 Tab 读取配置需同时具备 `config.read` 和 `captcha.read`；修改还需 `config.update`。缺少 `captcha.read` 时不得用默认值冒充已保存状态，也不得开放人机验证写入。若以后需要让站点管理员独立于验证服务权限管理此策略，应另行设计后端字段级授权和 API，不能仅扩大前端菜单权限。站点策略页面按 Tab 的权限组合显示可访问面板：访问与验证需要 `config.read + captcha.read`，内容规则需要 `config.read`，通知策略需要 `communications.read`。

## 5. 菜单设计规则

### 5.1 按频次排序

- 内容和用户放在前面，服务日常运营。
- 站点放在中间，修改频率低于内容处理但高于系统排障。
- 系统放在最后，服务配置、监控和升级使用频率较低但风险较高。
- 组内先放列表和日常入口，再放配置、诊断和高风险入口。

### 5.2 页面只归属一个主入口

一个页面只能有一个主菜单归属。相关设置使用同一页面内的 Tab 组织，不在侧栏重复出现；跨域入口使用页面内链接或快捷入口。

例：

- 文件管理只在“内容”出现；存储服务页面提供“查看文件管理”的关联链接。
- 站点策略只在“站点”出现；通知处理页面提供“查看通知策略”的关联链接。
- 验证服务只在“系统”出现；站点策略的访问与验证 Tab 提供“配置验证服务”的依赖链接。

### 5.3 技术词只出现在技术信息

Gateway、Worker、Outbox、Handler、CAS、驱动 slug 和内部配置键可以出现在页面的高级诊断或技术信息中，不作为管理员默认入口名称。

### 5.4 权限不随菜单改名

菜单调整只改变发现路径，不改变后端授权。现有 capability、数据范围、API 和旧路由继续有效。需要拆分页面时，读权限和写权限仍分别判断。

本文件是管理端菜单归属、中文名称和导航顺序的当前规范。`ADMIN-IA-DESIGN.md` 的旧路由地图仅作迁移历史；新增或迁移页面须先更新本文件，再同步 `apps/admin/config/navigation.ts`、页面标题与面包屑、相关 E2E 断言。路径和 capability 变更仍需独立审查，不能以菜单文案调整代替。

## 6. 路由迁移规范

新菜单可以先使用已有 URL，避免无意义的路由迁移。旧 URL 必须继续作为兼容入口，并在导航中只显示新的中文名称。

| 菜单名称 | 当前 URL | 迁移要求 |
|---|---|---|
| 内容 → 文件管理 | `/apps/settings/storage/files` | 保留 URL，菜单域改为内容 |
| 站点 → 站点策略 | `/apps/settings/site/policies` | 新规范入口；Tab 包含访问与验证、内容规则、通知策略 |
| 系统 → 验证服务 | `/apps/settings/verification` | 保留 URL，页面只管理系统验证服务 |
| 旧访问入口 | `/apps/settings/access` | 重定向到站点策略 `tab=access`，保留书签兼容 |
| 旧内容规则入口 | `/apps/settings/community-rules` | 重定向到站点策略 `tab=content`，保留书签兼容 |
| 旧通知策略入口 | `/apps/operations/notification-policies` | 重定向到站点策略 `tab=notifications`，保留书签兼容 |

只有在多个页面已经稳定使用新入口后，才评估是否增加规范化路由。删除旧路由、修改 API 路径或修改 capability 必须单独立项。

## 7. 页面文案规范

- 页面标题使用管理员能直接理解的业务名：`站点策略`、`验证服务`；Tab 使用 `访问与验证`、`内容规则`、`通知策略`。
- 页面副标题说明影响范围，不描述内部实现。
- 页面内部可以使用小节标题解释技术细节，但不把技术名词当作主标题。
- 保存按钮必须说明保存范围，例如“保存访问设置”“保存内容规则”“保存验证服务设置”。
- 配置失败时显示“设置未生效”的原因和依赖项，不只显示“保存成功”。

## 8. 验收标准

菜单调整完成后，至少验证：

1. 具有对应读取权限的管理员能看到内容、用户、站点、系统四组中的正确入口。
2. 无写权限的管理员仍能只读查看允许的页面，编辑控件单独隐藏。
3. 旧 URL、面包屑、页面内跳转和浏览器后退继续可用。
4. 注册邮件验证和人机验证不再与系统验证码服务设置混在同一表单；三类站点策略在同一页面通过 Tab 切换。
5. 文件管理、通知策略、通知处理、存储服务的归属符合本规范。
6. 技术闸口和管理端构建通过，dev 浏览器可看到新菜单。

# 授权边界规范

## 内容与评论

- 卡片正文、媒体、标签等内容：作者可编辑和删除自己的资源；管理员可管理任意资源，但仍由后端能力与归属策略最终裁决。
- 普通用户发布后不能编辑评论正文，只能删除自己的评论。后台管理员可通过 `comments.update.all` 修正正文，通过 `comments.moderate.all` 修改审核状态，通过 `comments.pin.all` 管理每张卡片唯一的置顶评论，通过 `comments.delete.all` 删除评论；所有后台变更必须提交原因并写入审计。
- 评论置顶是 `card_comment_pins` 表中的卡片级关系，不再接受 `comments.is_top` 写入。只允许置顶当前卡片下可见、未删除的一级评论；隐藏、封禁、退审、删除评论或删除卡片时自动解除关系。
- 审核中的评论保持不可见；只有审核通过后，评论、回复、提及和相关通知才允许发布。

## 实现要求

- 前端动作只根据会话返回的 capability/grant 显示，不得用“是否登录”或“是否进入后台”替代权限判断。
- 每个写接口必须同时具备路由权限检查和服务层的能力/归属检查；批量接口按具体操作再次检查能力。
- 变更资源正文、状态、删除和恢复必须使用独立能力，不能复用宽泛的读取权限。
- SDK、路由契约、管理端按钮和测试必须在同一次接口变更中同步更新；生成物不得保留已删除的 endpoint。
- 资源不存在、无权访问和已删除资源应保持稳定的 HTTP 状态/错误码，前端据此显示不同空态。

## 管理端垂直授权

- `*.all` 或 `*.global` 只授予某类动作的入口，不代表操作者可以越过自己的权限层级管理任意账号或角色。
- 角色能力变更必须以操作者的 `GrantSet` 为授权上限：非 root 不能写入自己不拥有的 capability/scope，不能修改自己正在使用的角色，也不能修改当前能力高于自己的角色。
- root 系统角色只能由 root 操作者修改；破坏性角色 reseed 仅允许 root 执行。
- 用户资料、状态、删除、角色分配、批量管理和 Session 撤销都必须在 Service/Application 层比较操作者与目标的角色和 grants。非 root 不能操作 root 或权限高于自己的目标。
- 非 root 不能通过管理接口修改自己的角色。任何删除、禁用或移除 root 角色的事务，提交后必须仍至少存在一名状态允许登录且未删除的 root 用户。
- root 身份以 `config('system.system_roles.root')` 的角色锚点判断，不能用用户名、展示名称或前端页面身份推断。
- 用户安全概览当前是只读入口；管理端已移除独立账号恢复记录页，恢复操作通过审计日志追溯。若以后增加会改变 Session、凭据或恢复状态的动作，必须复用同一目标层级边界。
- `users.security` 响应通过 `session_mutation_allowed` 返回当前 actor 对目标用户的服务端判定。该字段不包含角色或 grants；Session 撤销接口仍须重新授权。专职安全角色不需要拥有目标用户的内容类 grants，但非 root 仍不能撤销 root 用户的 Session。

## 回归检查

涉及权限的改动至少覆盖：本人/他人、普通用户/管理员、自通知或重复消费（如适用）、审核中资源、已删除资源，以及前端无权限时不显示动作按钮。

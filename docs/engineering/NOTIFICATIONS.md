# 站内通知开发规范

> 2026-11-11 策略修订：完整规则身份、事务快照与审计按 [收敛设计](PLATFORM-CONVERGENCE-2026-11-11.md) 实施。历史 NULL 版本与非 NULL 冻结快照读取失败须分开；后者不得解释为未配置并放行。

本文是 LoveCards 站内通知的唯一设计规则源。任何新增或修改会影响用户权益、账号安全、内容审核、互动提醒或站内公告的用例，都必须先按本文完成通知判定；具体事件投递机制见 [EVENTING.md](EVENTING.md)。

## 1. 通知的职责

站内通知用于保存“某个用户离开当前请求后仍需要知道或处理的既成事实”。它是持久、可读取、可幂等恢复的用户收件记录，不是通用消息总线。

以下概念必须分开：

| 机制 | 面向谁 | 典型用途 | 是否进入通知中心 |
| --- | --- | --- | --- |
| 请求内提示 | 当前操作者 | 表单错误、保存成功、权限不足 | 否 |
| 互动通知 | 内容作者或关系用户 | 点赞、收藏、评论、回复、关注、私信、@提及 | 是 |
| 系统通知 | 被平台行为影响的用户 | 账号安全、审核决定、权限或访问状态变化、站内公告 | 是 |
| 审计日志 | 管理员与调查人员 | 谁在何时执行了高风险操作 | 否 |
| 运维告警 | 值班与运维系统 | Worker 故障、投递积压、存储或数据库异常 | 否 |

同一个高风险用例可以同时写审计和发送系统通知；两者不能互相替代。运维告警也不能只依赖它所监控的通知队列。

## 2. 强制判定流程

新增业务状态转换时依次回答：

1. 是否存在一个明确的受影响用户？没有则使用日志、审计或运维告警，不创建站内通知。
2. 该事实是否在当前请求结束后仍会影响用户的安全、权限、内容可见性、资产、关系或待办？是则必须创建通知。
3. 事实是否由另一名普通用户的互动产生？是则使用对应业务事件和互动/社交/消息通知，不得伪装成 `system.*`。
4. 事实是否由可信后端、审核流程或管理员操作产生？是则使用 `SystemNoticeIssuer` 发布受控系统通知。
5. 当前操作是否只是请求失败、未发生状态变化、撤销互动或重复提交？是则不得创建新通知。

代码评审不能以“前端已经弹出提示”作为不发送通知的理由，也不能以“以后可能有用”为每个 CRUD 增加通知。

## 3. 必须使用系统通知的场景

只要系统已经具备对应事实和收件人，下列成功状态转换必须使用系统通知：

### 3.1 账号与安全

- 密码通过找回流程重置；
- 管理员修改密码、邮箱、手机号或账号角色；
- 单个或全部登录 Session 被管理员撤销；
- 账号被封禁、解除封禁、隐藏、恢复、进入或离开审核状态；
- 已实现可信检测的新设备登录、异常登录或安全策略命中。

安全操作仍必须增加 `security_version`、撤销 Session 或写审计时，通知只能作为补充，不能代替这些控制。

### 3.2 审核与治理

- 卡片或评论由待审核变为公开；
- 卡片、评论或账号被审核驳回、隐藏、封禁或恢复，且结果会影响当事人；
- 用户提交的举报进入对用户有意义的终态，例如已处理或未予处理；
- 管理员作出的其他会改变用户内容可见性或使用权限的决定。

“进入审核队列”“管理员打开详情”“只追加内部备注”等内部过程不通知。开启先审后发时，只能在审核通过且资源真实可见后通知。

### 3.3 平台告知

- 需要指定用户采取后续动作的服务变更；
- 已有明确收件范围、发布权限和幂等批次号的站内公告；
- 会影响用户访问、权益或数据处理结果的后台任务终态。

批量公告在拥有独立的受信发布入口、收件范围快照、批次幂等和审计前不得通过客户端临时拼装。

## 4. 不得使用系统通知的场景

- 点赞、收藏、关注、评论、回复、私信和 @提及；这些使用已有业务事件类型；
- 登录失败、表单校验失败、网络错误、保存成功等当前请求反馈；
- 取消点赞、取消收藏、取消关注等撤销动作，除非产品另有明确的安全或权益语义；
- 没有真实状态变化的重复审核、重复封禁、重复恢复或重复 Session 撤销；
- 只供管理员调查的内部备注、堆栈、投递错误和基础设施指标；
- 已删除且无法再访问通知中心的账号；
- 客户端自行提交的任意 `message`、`severity` 或外部 URL。

## 5. 类型和严重级别

| 类型 | 使用条件 | 常用级别 | 示例 |
| --- | --- | --- | --- |
| `system.notice` | 中性平台告知或待办 | `info`、`success`、`warning` | 服务变更、任务完成、站内公告 |
| `system.security` | 凭证、Session、权限或账号风险 | `warning`、`critical` | 改密、角色变化、撤销 Session |
| `system.moderation` | 审核、举报和账号/内容治理结果 | `info`、`success`、`warning`、`critical` | 审核通过、举报结果、封禁或恢复 |

`system.notification.issued` 的冻结策略快照以 `system.*` 表示上述系统通知类型集合；现行规则行中的 `system.moderation` 是历史默认实例类型。两者的已知差异在策略更新前按这一条明确映射核验，不改写历史快照，也不放宽其他事件或类型漂移的校验。

严重级别表达影响程度，不表达投递优先级：

- `info`：无需紧急处理的中性结果；
- `success`：用户发起流程的正向终态；
- `warning`：需要关注但账号仍可安全使用；
- `critical`：凭证、访问权或高风险治理发生重大变化。

不得为了获得醒目样式滥用 `critical`。

## 6. 发布、事务与幂等

系统通知必须通过 `SystemNoticeIssuer` 发布 `system.notification.issued`，普通业务模块不得直接写 `notifications` 表。互动通知必须通过 `DomainEventBus` 发布所属业务事实，由 Notifications Handler 投影；前端不得创建通知或调用“触发通知”接口。

必须遵守：

1. 先确认真实状态转换，再在同一数据库事务中写业务数据和 Outbox 事件；事务回滚时两者一起消失。
2. 事件记录的是已经发生的事实，不能提前发布“即将成功”。
3. Handler 按至少一次投递设计，使用通知 `dedupe_key` 或 `DeliveryContext::idempotencyKey()` 幂等。
4. 重复请求、事件重放和 Worker 崩溃恢复不得产生重复通知。
5. 同一资源未来再次发生新的真实状态循环时必须能够产生新通知，不能使用永久吞掉后续变化的固定键。

推荐幂等键：

| 事实 | 推荐键组成 |
| --- | --- |
| 一次互动关系 | 关系类型 + 资源 ID + actor ID |
| 一次内容审核转换 | 资源类型 + 资源 ID + 目标状态或状态版本 |
| 账号状态或权限变化 | 用户 ID + `security_version` + 变化类型 |
| 单 Session 撤销 | Session ID |
| 全 Session 撤销 | 排序后的受影响 Session ID 集合摘要 |
| 批量公告 | 公告批次 ID + recipient ID |

幂等键必须来自稳定、持久化的业务事实，长度符合 `NotificationIntent` 限制；不得使用随机数、当前时间或通知文案。缺少 revision、版本或批次 ID 的状态流必须先补足稳定事实，不能用时间戳掩盖模型缺口。

## 7. 收件人与身份规则

- 所有通知统一排除 `actor_id === recipient_id`；系统身份使用 `actor_id = null`。
- 互动与提及只解析可参与对应业务的有效用户；排除已注销、受限和重复收件人。
- 隐藏用户仍保留账号访问能力时可以接收普通通知；其身份不能在其他用户的通知中显示为可点击公开主页。
- 封禁或待审核用户的系统通知可以持久化，供其状态恢复后读取；普通互动通知按账号可参与状态过滤。
- 已软删除或永久删除的用户不创建新通知。
- 通知列表批量装配 actor 的真实 `username` 与 `avatar`；失效身份返回稳定的 `actor_state`，前端不得逐条查询或猜 handle。

## 8. Payload、链接与资源失效

系统通知 payload 只允许：

```json
{
  "message": "受控的用户可见文案",
  "action_url": "/settings",
  "severity": "warning"
}
```

- `action_url` 必须是经过服务端验证的站内绝对路径；禁止协议、域名、双斜线、反斜线和客户端提供的任意跳转。
- 文案不得包含密码、Token、邮箱验证码、内部堆栈、IP 全量记录或其他敏感数据。
- 互动通知使用受控资源引用，不把整份内容快照复制进 payload。
- 列表读取时必须重新判断资源和成员资格；资源删除或不可访问时返回稳定的 `resource_state` 和空 `action_url`，前端显示不可访问占位。

## 9. 前后端边界

后端负责：触发判断、收件人解析、状态可见性、去重、actor 装配、资源状态和安全 `action_url`。

SDK 负责：暴露通知列表、未读数、已读操作和稳定字段类型，不增加业务触发方法。

通知列表与未读/批量已读查询可以使用 `NotificationListCategory`；其中 `engagement` 只是服务端联合筛选值，不能出现在 `NotificationItem.category` 中。联合列表必须由服务端按 `created_at DESC, id DESC` 使用不透明游标分页，前端不得分别请求后拼接或推算未读总数。省略分类的未读与批量已读保持全局语义。

前端只负责：

- 消费 SDK 返回的 `type/category/payload/actor/resource_state/action_url`；
- 展示 loading、空态、错误态、不可访问占位和未读状态；
- 只按后端返回的 `action_url` 导航；
- 不解析 @username、不查询每条 actor、不猜资源路由、不在点赞等请求成功后补发通知。

请求成功 Toast 与通知中心记录是两套体验：前者反馈当前操作者，后者告知被影响的收件人。

## 10. 新增通知的实现顺序

1. 写清业务事实、唯一收件人规则、排除条件和何时算真实状态转换。
2. 选择已有事件；只有不存在稳定业务事实时才新增事件类型与版本。
3. 在业务事务内发布事件或调用 `SystemNoticeIssuer`。
4. 在 Notifications 模块注册 Handler，并生成 `NotificationIntent` 与稳定 `dedupe_key`。
5. 扩展 `NotificationTypeCatalog`（仅新增公开类型时）、读取模型与 SDK 类型；系统通知优先复用三种既有类型。
6. 前端只在 SDK 契约就绪后消费通知展示字段，不增加触发请求；后台策略名称与影响说明由管理 API Resource 提供。
7. 更新 [EVENTING.md](EVENTING.md) 的当前事件表和必要的前端交接说明。

若新增事件需要出现在后台“通知策略”，还须在前向迁移中增加当前策略规则、在管理 API Resource 中补中文名称和影响说明，并验证该规则与 `HandlerRegistry` 的通知处理器一致。策略表保存开关与历史版本，Resource 只提供展示文案；不得从处理器注册自动改写策略表。当前策略按 `event_type` 开关，同名事件的不同 `event_version` 不构成独立开关。

## 11. 强制测试与评审清单

每个新触发至少覆盖：

- 成功状态转换只产生一条通知；
- 自通知被排除；
- 无状态变化、撤销动作或重复请求不产生通知；
- Outbox/业务事务回滚后没有事件和通知投递；
- 同一事件重复消费只保留一条通知；
- 审核中资源不通知，审核通过并可见后才通知；
- 已删除、受限、隐藏、封禁用户按第 7 节规则处理；
- actor 注销或资源删除后读取模型返回正确失效状态；
- `action_url` 拒绝外部、协议相对和编码绕过路径；
- payload 不包含敏感字段，前端能处理 loading、空、错误和不可访问状态。

提交前执行受影响 PHP 语法检查、`npm run test:backend` 和根 `npm run check`。新增真实 API 契约时，继续按 [BACKEND-TESTING.md](BACKEND-TESTING.md) 完成 SDK 集成和相应 E2E；审计与运维告警边界见 [OBSERVABILITY.md](OBSERVABILITY.md)，前端消费契约见 [FRONTEND-AGENT-HANDOFF.md](FRONTEND-AGENT-HANDOFF.md)。

## 12. 当前触发基线

当前已经接入并作为回归基线的场景：关注、私信、卡片/评论点赞、卡片收藏、评论、回复、卡片/评论 @提及、卡片/评论审核通过、举报终态、密码找回成功、管理员改单个或全部 Session、管理员修改密码/联系方式/角色，以及用户账号状态治理。

新设备检测、全站公告和更细粒度的内容治理结果只有在对应业务事实、权限入口与持久化 revision/批次存在后接入；现有卡片/评论 toggle 在补齐显式审核决定和稳定 moderation revision 前不得用当前时间伪造通知幂等键，也不能由前端或临时代码模拟。
